# Consent and reset (milestone 7, post-tag)

**18 Oct 2026.** Khalil's instruction of 18 Oct 2026, after the milestone 9a close-out: report where consent is stored and what the wallet's reset and `migrate` do with it; make both put every seed user back to not consented; a Reset control in the console next to the fault panel, behind the admin key; the consent screen on opening the chat, before any typing, with the first-request gate kept as the fallback; two journeys; the record under milestone 7's post-tag notes in `docs/build-plan.md`.

## Findings (the report)

- Consent is stored in the **wallet** database only: `User.ConsentGiven` (`src/Wallet.MockApi/Data/Entities/User.cs`), read by the agent through `GET /users/{id}` and set through `POST /users/{id}/consent`. The agent database holds no consent; `Conversation.ConsentShown` is per conversation and in memory.
- Neither `POST /admin/reset` nor `migrate` puts consent back to not consented for every user. Both apply the seed as it is, and the seed's `data/seed/users.json` says `consent_given` true for U1 to U4 and false for U5 ("First use: has not given consent yet"). After either, only U5 sees the consent screen.
- The seed is Khalil's and is never edited (its hash is frozen). The development set (95 cases, 75 on U1, none on U5) and the sealed held-out set were keyed for the seed's roles: U1 to U4 consented, U5 not. The runner resets the wallet before every case, so a reset that cleared consent for every user would put the consent screen in front of every case and break every key.

## Ruling A (controller, for Khalil to confirm or overturn)

The wallet's reset and a fresh `migrate` clear consent for every user, as instructed, and this is the default. The seed's `consent_given` values stay the test set's roles and can be asked for: `POST /admin/reset?consent=seed` restores them. The runner, the test fixtures and the journeys' per-test reset ask for the seed's values, so no answer key, target or seed file changes. The console's Reset control and the documented hand command use the default, so the demo starts with every user unconsented.

## Console panels follow the phone (18 Oct 2026, Khalil's third message)

Khalil: the console's aliases panel does not refresh after an alias is added or deleted from the phone; every console panel that mirrors wallet state (wallet data, aliases, log) must update after a phone action, through the same change notification the wallet-data panel uses after a payment. The controller's reproduction (headless, 18 Oct 2026): within one browser tab the three phone paths (directory save, directory delete, the offer's Save) do refresh the aliases panel through `ChatSession.WalletVersion`; what cannot work today is a second tab or window (every tab is its own circuit with its own `ChatSession`, and no circuit hears another's actions), and, since the Reset control of item 3, a restarted conversation's version starts again at 0 while a panel still holds the old count, so a later change can match the stale number and be missed. Both go with one process-wide notification.

10. **A process-wide wallet-change notification.**
    - New singleton `WalletChanges` in `src/Agent.Web/Services/` (registered in `AddAgentWebServices`): `event Action<WalletChange>? Changed`, `void Raise(WalletChange change)`, and `public sealed record WalletChange(int UserId, WalletChangeKind Kind)` with `enum WalletChangeKind { Payment, Alias, Reset }`. `Raise` invokes every handler and never lets one handler's exception stop the others or reach the caller (caught, logged at Warning through `ILogger<WalletChanges>` with the handler's exception type only). Handlers may be called on any thread; subscribers marshal with `InvokeAsync`.
    - Who raises: `ChatSession` raises `Payment` or `Alias` for its demo user whenever its conversation's `WalletVersion` goes up (`OnConversationChanged` compares with the last version it saw; `Conversation` says which: a `Done` outcome is a payment, `SaveAliasAsync` and the directory actions are aliases: expose that as `Conversation.LastWalletChange` or raise from the three places through a small callback, the implementer's choice, documented). `ResetPanel` raises `Reset` after the wallet's reset succeeded (before `RestartAsync`), for user 0 meaning every user. The console's own aliases panel acts through `ChatSession`, so it is covered.
    - `ChatSession.WalletVersion` becomes monotonic across `RestartAsync`: a base that grows by the previous conversation's version plus one at every restart, so a restart itself is a new version and the phone's `DirectoryPanel` reloads the seed's list after a Reset (it is stale today).
