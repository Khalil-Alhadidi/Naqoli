# Failure modes

How the system can fail and what it does. One row per mode. Added to whenever a new one is found. The six modes from slide 2 are completed in milestone 8.

| Mode | What the system does | Where handled | Test |
|---|---|---|---|
| Wallet times out after execute, status unknown | Pending moves to Checking, the user sees "checking", never "failed". The executor settles it by resending the same body with the same idempotency key (it executes once or replays; 409 means keep checking); `GET /transactions/by-key` is for display, and its 404 is final only once the original call has definitely ended | Milestone 3 executor, milestone 8 screen | pending |
| Double tap on Confirm | A pending record leaves Pending once; the second tap does nothing | Milestone 3 pending store | pending |
| Card timer ends | Record becomes Expired; Confirm is disabled; "Try again" rebuilds a new record | Milestone 3 and 4 | pending |
| Balance changes between card and tap | Recheck at execute fails the record as NotDone with a template reply | Milestone 3 | pending |
| Wallet rejects the execute | NotDone, template reply, no retry without a new tap | Milestone 3 | pending |
| Model outage or timeout | Handover message from a template; no card | Milestone 6 | pending |
| Invalid or unexpected model output | Becomes a question to the user, never an exception or a card | Milestone 6 | pending |
| Connection string missing, or SQL Server unreachable, when `migrate` runs | One clear line to stderr and exit 1 | Milestone 1, src/Wallet.MockApi/Program.cs and Data/WalletConnection.cs | review only (returns before the host is built; unreachable-server path exercised by hand) |
| Windows path longer than about 100 characters | `dotnet build` fails with MSB3021 from the Playwright package; README tells the reader to clone to a short path or enable long paths | README, Prerequisites | reproduced by hand on 14 Oct 2026 |
| Seeding fails part way (SQL error during `migrate` or reset) | `SeedData.Apply` and `SeedReset.ResetAsync` run in one database transaction, so a failure leaves no half seed that the "users exist" check would then treat as complete | Milestone 2 and 2b, src/Wallet.MockApi/Data/SeedData.cs and SeedReset.cs | review only (`SeedApplyTests.ApplyTwiceDoesNotDuplicateRows` and `ResetRestoresIdentitiesFromOne` cover a second apply and a reset, not a failure in the middle of one) |
| Reset on a table that never held a row | `DBCC CHECKIDENT ... RESEED, 0` would make the next identity 0, not 1; the reset (and the `AdoptTestSeed` migration's wipe) reseeds only tables whose `last_value` is set, so ids always start at 1 | Milestone 2, src/Wallet.MockApi/Data/SeedReset.cs; milestone 2b, Migrations/20261014104803_AdoptTestSeed.cs | review only (`SeedApplyTests.ResetRestoresIdentitiesFromOne` checks ids from 1 after a reset, but every table has held rows by then, so the never-populated branch is not exercised) |
| Two execute calls with the same idempotency key (double tap, client retry during a slow call) | A known key is looked up first and replays its stored outcome at once (200 Done, the original 422 for a stored failure). When both calls arrive before either has written, the unique index on `Transactions.IdempotencyKey` lets one insert win; the other waits on the index, gets SQL error 2601/2627 and replays. Money moves once | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.SameKeyTwiceExecutesOnce, TwoConcurrentCallsWithTheSameKeyExecuteOnce (opt-in SQL) |
| Two different payments race for the same balance | The debit is one conditional update (`BalanceIqd >= total` in its `Where`); the second sees zero rows, is stored as Failed `insufficient_funds` and returns 422. A balance never goes below zero | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.TwoConcurrentAffordableTransfersNeverOverdraw (opt-in SQL) |
| Two payments of the same bill with different keys | The bill is cleared only where the amount due still equals the quoted amount; the loser is refunded inside the same database transaction and stored as Failed `nothing_due` (or, if the winner has already committed, refused by validation with `nothing_due`) | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.TwoConcurrentPaymentsOfOneBillPayOnce (opt-in SQL) |
| Retry of a key whose first call changed the data the request is checked against (a paid bill is now "nothing due") | A known key replays its stored outcome before validation and before the PIN check, so a retry never depends on the body or on changed data, and a PIN on a known key costs no attempt and changes no user row. A refusal looks the key up once more, for a same-key call that committed meanwhile | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.BillPaymentZeroesTheAmountDue (opt-in SQL) |
| A reset runs while a payment is executing, or two resets run at once | `WalletGate` (a singleton): payments enter shared, a reset enters exclusive, waits for payments inside to leave and holds new ones back until it is done. Entered before any database transaction opens, released in `finally`; fault delays are outside it, so a hanging request never blocks a reset | Milestone 2, src/Wallet.MockApi/Services/WalletGate.cs, TransactionService.cs, Endpoints/AdminEndpoints.cs | review only |
| The caller disconnects during an injected delay | Delays honour the request's cancellation token. Before execute nothing has been written; after execute the transaction is already committed, the cancelled wait is swallowed and the stored result stands, found by its key. A by-key 404 is final only once the original call has ended; until then, settle by resending with the same key | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.TimeoutAfterExecuteIsFoundByKeyWhileTheRequestStillHangs (opt-in SQL) |
| Admin endpoints reachable without a key outside Development, or from a web page on the demo machine | With no `Wallet:AdminKey`, `/admin` routes are open in Development only, and only to requests that carry the `X-Wallet-Admin-Key` header (any value): a custom header forces a browser preflight, which the API never grants, so a page cannot reset the wallet. Elsewhere they return 403 `admin_key_required`. With a key (at least 16 characters, checked at start-up), the header must match (constant-time compare) | Milestone 2, src/Wallet.MockApi/AdminKeyFilter.cs and WalletOptions.cs | FaultTests.AdminKeyRequiredWhenConfigured, AdminIsClosedOutsideDevelopmentWithoutKey, AdminNeedsTheHeaderInDevelopmentWithoutKey (opt-in SQL) |
| A fault set with `once` is seen by two concurrent payments | `FaultSwitch.Take` reads and clears under one lock, so only one payment gets it | Milestone 2, src/Wallet.MockApi/Services/FaultSwitch.cs | FaultTests.OnceFaultClearsAfterOneRequest (opt-in SQL; sequential) |
| Wallet returns an error on execute (fault `error`) | 500 `injected_error` before anything is written; the key stays unknown (by-key 404), so a retry with the same key executes normally | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs and FaultSwitch.cs; agent-side handling in milestone 3 | FaultTests.ErrorFaultReturns500AndMovesNothing, OnceFaultClearsAfterOneRequest (opt-in SQL) |
| Wallet answers slowly (fault `slow`) | The execute waits `delayMs`, then runs normally and returns 201. Nothing is written while it waits, so by-key is 404 for a payment that will still run (see the slow-fault-longer-than-the-client-timeout row) | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.SlowFaultDelaysButSucceeds (opt-in SQL) |
| Wallet times out before execute (fault `timeoutBeforeExecute`) | Waits `delayMs`, then 504 `injected_timeout`; nothing is written and by-key is 404 `unknown_key`. The 504 ends the call, so here the 404 is final: not done | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.TimeoutBeforeExecuteMovesNothingAndByKeyIs404 (opt-in SQL) |
| Wallet times out after execute (fault `timeoutAfterExecute`), wallet side | The payment commits first, then the response is held for `delayMs`; `GET /transactions/by-key/{key}` already returns the `done` row while the request hangs. The gate is released before the delay, so a reset may run meanwhile: the hanging request then returns 201 for a transaction the reset has deleted, which is the intended "client does not know the outcome" case (the agent expires its pending records on reset, milestone 3) | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs and Endpoints/TransactionEndpoints.cs | FaultTests.TimeoutAfterExecuteIsFoundByKeyWhileTheRequestStillHangs (opt-in SQL) |
| PIN entered wrong repeatedly, one at a time or many at once | Each check first reserves an attempt with one conditional update on the user row (unlocked and unchanged since read; it locks the PIN when it takes the last attempt), and only then runs PBKDF2, so concurrent guesses cannot all see the PIN unlocked: at most `Wallet:MaxPinAttempts` wrong PINs are checked before the lock. Each wrong PIN is 422 `pin_invalid` with `attemptsLeft`; once locked, every payment that checks the PIN is 423 `pin_locked`, even with the right PIN, until `POST /admin/reset`. A right PIN gives its attempt back and clears a lock only if it set it itself. Nothing moves; the PIN is never echoed or logged | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.ThreeWrongPinsLockTheUser, ConcurrentWrongPinsCannotExceedTheLockout (opt-in SQL) |
| Payment larger than the balance | The quote reports `sufficient: false` but does not refuse; the execute's conditional debit finds no row, the transaction is stored as Failed `insufficient_funds` and 422 is returned. Nothing moves | Milestone 2, src/Wallet.MockApi/Services/PaymentValidator.cs and TransactionService.cs | TransactionTests.InsufficientFundsIs422AndNothingMoves (opt-in SQL) |
| Two opposite-direction transfers deadlock on the account rows | SQL Server kills one (error 1205); it surfaces as 500 without a `code` extension, with nothing committed; the client treats it as unknown and a retry with the same key executes | Milestone 2 TransactionService; agent-side retry in milestone 3 | review only (not reproduced; documented from the lock order) |
| Slow fault longer than the client timeout | The client gives up while its request is still queued behind the delay; by-key is 404 (nothing written yet), then the request runs and the key becomes `done`. A by-key 404 is therefore not final while the original call may still be running | Milestone 3 executor: settles Checking by resending the same body with the same key (runs once or replays; 409 keep checking), never by trusting a by-key 404 | review only |
| The caller disconnects while the payment is committing | Once the debit has run, the rest of the payment and its commit run without the request's cancellation token, so the commit is never cancelled half-way; the outcome is stored and found by its key | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | review only |
| Idempotency keys that differ only in case, or carry unexpected characters | A key must match `^[A-Za-z0-9_-]{1,64}$`, else 400 `invalid_idempotency_key` (by-key: 404 `unknown_key`). Keys compare under the database collation, which is case-insensitive by default, so `AbC` and `abc` are one key: the safe direction (a retry never runs twice). The agent sends lower-case GUIDs | Milestone 2, src/Wallet.MockApi/Endpoints/TransactionEndpoints.cs and Services/TransactionService.cs; key choice in milestone 3 | TransactionTests.MalformedKeyIs400 (opt-in SQL) |
| Any 500 without a `code` extension (deadlock victim, lost connection, unhandled exception) or a transport failure on execute | The outcome is unknown: treated as Checking, never as Failed, and settled by resending with the same key | Milestone 3 executor | pending |
| Seed files missing or invalid at start (file absent, not JSON, unknown or missing member, null in a required value, dangling reference, duplicate id, value not allowed) | `SeedSet.Load` throws `SeedException`, whose message starts with the file name. The `SeedSet` singleton is resolved at start-up, so the API does not start; `migrate` prints the message to stderr and exits 1. `seed-hash` names the missing file and fails | Milestone 2b, src/Wallet.MockApi/Data/Seed/SeedSet.cs and Program.cs | SeedSetTests.MissingFileNamesTheFile, UnknownPropertyIsRejected, DanglingContactNumberIsRejected, MissingRequiredPropertyIsRejected, NullRequiredValueIsRejected; SeedHashTests.MissingFileNamesTheFile |
| A seed file changed by hand (or a new export dropped in) | `SeedHash.Compute` over the files no longer equals `data/seed/seed-hash.txt`, so `SeedHashTests.SeedHashMatchesCommittedValue` fails. If the change is intended (a new export from Khalil): run `dotnet run --project src/Wallet.MockApi --no-launch-profile -- seed-hash`, write the last line printed to `seed-hash.txt`, re-check every answer key and tag the new seed. Otherwise undo the change. Line endings do not count (`
` is removed before hashing) | Milestone 2b, src/Wallet.MockApi/Data/Seed/SeedHash.cs; procedure in data/seed/README.md | SeedHashTests.SeedHashMatchesCommittedValue, OneChangedByteChangesTheHash, CrlfAndLfHashTheSame |
| A seed file saved with a UTF-8 byte order mark (some Windows editors add one) | The JSON reader refuses the leading BOM; `SeedSet.Load` wraps the error in `SeedException` naming the file, so the start fails as for any invalid file. The bytes also change the hash. Save the file as UTF-8 without BOM, or take Khalil's export as it was | Milestone 2b, src/Wallet.MockApi/Data/Seed/SeedSet.cs | review only |
| Transfer to a closed account (contact S20's `07805550120`, or `07805550193`) | `PaymentValidator` refuses it with 422 `account_closed` on quote and execute, whether named by phone or by id, after `unknown_recipient` and before `same_account`. It is a validation refusal: nothing moves, no row is written, by-key stays 404 and a retry with the same key is refused the same way. `GET /accounts/by-phone` and the contact list show `closed` beforehand | Milestone 2b, src/Wallet.MockApi/Services/PaymentValidator.cs; agent reply in milestone 7 | QuoteTests.QuoteToClosedAccountIsRefused, TransactionTests.TransferToClosedAccountIsRefusedAndNothingMoves (opt-in SQL) |
| A run crosses midnight Iraq time | Seeded history is dated from the Iraq date of the clock when the seed is applied, so a reset after midnight shifts every seeded date one day later than a reset before it. Within one reset the dates are fixed. The eval runner resets before every case (milestone 5), so one case never straddles the shift | Milestone 2b, src/Wallet.MockApi/Data/SeedData.cs (`TodayIn`, `IraqOffset`); runner in milestone 5 | review only (`ResetTests.ResetRestoresTheSeedExactly` would fail only if it crossed midnight itself) |
| Same-day history rows later than "now" | Two rows have `days_ago` 0 (H0045 at 12:07, H0043 at 16:36, both U3); in a run before those times they carry a time later than the clock. The wallet stores them as given, and history, `lastSentAt` and `since` filters show them as they are. The daily cap (milestone 7) must count them by Iraq date, as `data/README.md` says (everything with `days_ago` 0), not by "before now" | Milestone 2b, src/Wallet.MockApi/Data/SeedData.cs; daily cap in milestone 7 | review only |
