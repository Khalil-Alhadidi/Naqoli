# Failure modes

How the system can fail and what it does. One row per mode. Added to whenever a new one is found. The six modes from slide 2 are completed in milestone 8.

| Mode | What the system does | Where handled | Test |
|---|---|---|---|
| Wallet times out after execute, status unknown | Pending moves to Checking (`ConfirmOutcome.Checking`), the user sees "checking", never "failed". `ConfirmHandler.SettleCheckingAsync` settles it by resending the body rebuilt from the record with the same idempotency key: 201 or 200 is Done, a 4xx is NotDone (except a PIN refusal within `SettleWindowSeconds`, which stays Checking; see "Settle during a slow PIN payment"), another unknown outcome (5xx, timeout, 409 `in_progress`) stays Checking. `GET /transactions/by-key` is for display, and its 404 is final only once the original call has definitely ended | Milestone 3, src/Agent.Core/Confirm/ConfirmHandler.cs; screen in milestone 8 | ConfirmHandlerTests.TimeoutAfterExecuteIsCheckingThenDone, RetryReusesTheSameKey |
| Double tap on Confirm | A pending record leaves Pending once: the Confirm tap is one conditional update (`State = Pending` and the timer still running) to Executing, so of any number of taps exactly one gets `Begun` and the others get `AlreadyLeft(Executing)` and do nothing; only the winner writes an `executing` audit row and calls the wallet; the others get `ConfirmOutcome.AlreadyHandled` | Milestone 3, src/Agent.Core/Pending/PendingStore.cs (`TryBeginExecuteAsync`) and src/Agent.Core/Confirm/ConfirmHandler.cs | PendingStoreTests.BeginExecuteSucceedsOnce, ConcurrentBeginExecuteWinsOnce (20 parallel taps); ConfirmHandlerTests.DoubleTapExecutesOnce |
| Card timer ends, or Confirm arrives after it | Record becomes Expired (by `ExpireDueAsync`, which the hosted `PendingSweeper` runs every `SweepIntervalSeconds`, or by the late Confirm itself, which finds it Pending past `ExpiresAt`, marks it Expired and returns `Expired` without executing); a later tap gets `AlreadyLeft(Expired)`; Confirm is disabled; "Try again" rebuilds a new record | Milestone 3, src/Agent.Core/Pending/PendingStore.cs; screen in milestone 4 | PendingStoreTests.BeginExecuteOnExpiredMarksExpired, ExpireDueExpiresOnlyCardsPastTheirTimer; screen pending |
| Balance changes between card and tap | Before the execute, the Confirm handler reads the balance again (and the daily cap); a balance below the card's total ends the record as NotDone `insufficient_balance` and nothing is sent to the wallet. A read with no answer ends it as NotDone `not_done_nothing_taken` with detail `wallet_` and the reason | Milestone 3, src/Agent.Core/Confirm/ConfirmHandler.cs (`RecheckAsync`) | ConfirmHandlerTests.BalanceChangedAfterTheCard |
| Wallet rejects the execute | Any 4xx except 409 ends the record as NotDone with the wallet's code as its result code: `insufficient_funds` replies `insufficient_balance`, `nothing_due` and `account_closed` reply as themselves, every other code replies `not_done_nothing_taken` with the code as detail. The handover screen and the model parser that throws come in milestone 6 | Milestone 5, src/Agent.Core/Conversation/Conversation.cs; parser in milestone 6 | ConversationTests.AnUnavailableParserGivesModelUnavailableAndNoCard |
| Invalid or unexpected model output | Becomes a question to the user, never an exception or a card | Milestone 6 | pending |

| Two execute calls with the same idempotency key (double tap, client retry during a slow call) | A known key is looked up first and replays its stored outcome at once (200 Done, the original 422 for a stored failure).
