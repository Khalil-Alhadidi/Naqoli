# Failure modes

How the system can fail and what it does. The first section is the six failure modes of slide 2, in the slide's terms and order (Khalil, 16 Oct 2026, rejecting ruling 3 of the milestone 8 plan): for each, what could go wrong, how the agent handles it, and the named test or journey that shows it. The second section is how the faults are injected: the six faults of the switch, mapped to the modes they exercise. The table after them has one row per mode found, and is added to whenever a new one is found.

## The six failure modes of slide 2

What the user sees is given as the phone's outcome code and resource key, never the Arabic. "Wrong card" and "double payments" are targets of `docs/targets.md` that every runner report measures; the figures quoted are from the oracle run `docs/reports/dev-scripted-m8-wording-2026-10-16-1237` and the model reruns of 16 Oct 2026 (`docs/build-plan.md`, milestone 8).

## How the faults are injected

The six faults of the switch ([matching-rules.md](matching-rules.md), "Faults the switch must offer", Khalil, 14/10/2026) are how the modes above are exercised, on screen and in the runner; they are not the failure modes themselves. Each can be set to hit one call only (`once`), from the console's fault panel beside the live trace (the wallet's switch through `POST /admin/faults`, the model fault through `FaultingParser`, the external debit through `POST /admin/debit`; admin key `Console:WalletAdminKey`) or by a case's `fault` in the runner (`data/README.md`: `code`, `on`, `times`, `amount`). Double tap and a repeated request are user actions, not faults (their rows are below: "Double tap on Confirm"; the duplicate warning, journey `RepeatedRequestCarriesTheDuplicateWarning`).

| Fault (switch / case code) | What it does | Exercises mode | Shown by |
|---|---|---|---|
| `timeoutAfterExecute` / `wallet_timeout_after_execute` | The wallet commits the payment, then holds the answer for `delayMs` (the runner's `Eval:FaultDelayMs`, 12,000, above the agent's 10 s timeout) | 3: the agent times out after the money moved; Checking, then done by the resend under the same key, which the wallet replays | `TimeoutAfterExecuteShowsCheckingThenDone`; FLT-04; FaultTests.TimeoutAfterExecuteIsFoundByKeyWhileTheRequestStillHangs |
| `timeoutBeforeExecute` / `wallet_timeout_before_execute` | The wallet waits `delayMs`, then answers 504 `injected_timeout` with nothing written | 3, from the other side: the agent's timeout comes first, so the outcome is unknown to it; Checking, then done by the resend, which executes once because the fault has cleared | `TimeoutBeforeExecuteShowsCheckingThenResolves`; ConfirmHandlerTests.TimeoutBeforeExecuteIsCheckingThenDoneByResend; FaultTests.TimeoutBeforeExecuteMovesNothingAndByKeyIs404 |
| `error` / `wallet_error` | 500 `injected_error` before anything is written | 3's known-failure neighbour: a 5xx with a wallet code means nothing was taken, so the card ends `not_done` with `Refusal_not_done_nothing_taken` and `card-try-again` (a bare 5xx stays unknown and goes to Checking) | `WalletErrorEndsTheCardNotDone`; FLT-03; ConfirmHandlerTests.WalletErrorWithACodeIsNotDoneNothingTaken; FaultTests.ErrorFaultReturns500AndMovesNothing |

| model `invalid_reply` / `model_invalid_reply` | The next parse call returns `Unclear` with `Problem` `injected`, what the validator returns for a refused structure | 5, a reply that is not the structure (the refusal stop reason itself has no injected fault; its test drives the parser directly) | `ModelInvalidReplyIsNotUnderstood`; FaultingParserTests.AnInvalidReplyFaultIsUnclearWithProblemInjected; CaseDriverTests.AnInvalidModelReplyIsNotUnderstoodAndGradedAsModelInvalidReply |

Modes 1, 2 and 4 have no fault to inject: they are exercised by the development set's ambiguous, malformed and red-team cases (ADD-06 and ADD-07 type an instruction into the message) (every run reports wrong card and executions without a tap) and by the tests named in their rows.

In every one of the six the money moves at most once: the two timeout journeys and the runner's four fault-injection cases show zero double payments.
