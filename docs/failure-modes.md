# Failure modes

How the system can fail and what it does. One row per mode. Added to whenever a new one is found. The six modes from slide 2 are completed in milestone 8.

| Mode | What the system does | Where handled | Test |
|---|---|---|---|
| Wallet times out after execute, status unknown | Pending moves to Checking, the user sees "checking", never "failed"; a lookup by idempotency key resolves it | Milestone 3 executor, milestone 8 screen | pending |
| Double tap on Confirm | A pending record leaves Pending once; the second tap does nothing | Milestone 3 pending store | pending |
| Card timer ends | Record becomes Expired; Confirm is disabled; "Try again" rebuilds a new record | Milestone 3 and 4 | pending |
| Balance changes between card and tap | Recheck at execute fails the record as NotDone with a template reply | Milestone 3 | pending |
| Wallet rejects the execute | NotDone, template reply, no retry without a new tap | Milestone 3 | pending |
| Model outage or timeout | Handover message from a template; no card | Milestone 6 | pending |
| Invalid or unexpected model output | Becomes a question to the user, never an exception or a card | Milestone 6 | pending |
| Connection string missing, or SQL Server unreachable, when `migrate` runs | One clear line to stderr and exit 1 | Milestone 1, src/Wallet.MockApi/Program.cs and Data/WalletConnection.cs | review only (returns before the host is built; unreachable-server path exercised by hand) |
| Windows path longer than about 100 characters | `dotnet build` fails with MSB3021 from the Playwright package; README tells the reader to clone to a short path or enable long paths | README, Prerequisites | reproduced by hand on 14 Oct 2026 |
| Seeding fails part way (SQL error during `migrate` or reset) | `SeedData.Apply` and `SeedReset.Reset` run in one database transaction, so a failure leaves no half seed that the "users exist" check would then treat as complete | Milestone 2, src/Wallet.MockApi/Data/SeedData.cs and SeedReset.cs | SeedApplyTests (opt-in SQL) |
| Reset on a table that never held a row | `DBCC CHECKIDENT ... RESEED, 0` would make the next identity 0, not 1; the reset reseeds only tables whose `last_value` is set, so ids always start at 1 | Milestone 2, src/Wallet.MockApi/Data/SeedReset.cs | SeedApplyTests.ResetRestoresTheSeedWithIdentitiesFromOne (opt-in SQL) |
| Two execute calls with the same idempotency key at once (double tap, client retry during a slow call) | The unique index on `Transactions.IdempotencyKey` lets one insert win; the other waits on the index, gets SQL error 2601/2627 and returns the stored outcome (200 Done, the original 422 for a stored failure, 409 `in_progress` while executing). Money moves once | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.SameKeyTwiceExecutesOnce, TwoConcurrentCallsWithTheSameKeyExecuteOnce (opt-in SQL) |
| Two different payments race for the same balance | The debit is one conditional update (`BalanceIqd >= total` in its `Where`); the second sees zero rows, is stored as Failed `insufficient_funds` and returns 422. A balance never goes below zero | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.TwoConcurrentAffordableTransfersNeverOverdraw (opt-in SQL) |
| Two payments of the same bill with different keys | The bill is cleared only where the amount due still equals the quoted amount; the loser is refunded inside the same database transaction and stored as Failed `nothing_due` | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | review only |
| Retry of a key whose first call changed the data the request is checked against (a paid bill is now "nothing due") | A request refused by validation or the PIN rules first looks up its key; a known key returns its stored outcome, and a wrong PIN on a known key costs no attempt | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.BillPaymentZeroesTheAmountDue (opt-in SQL) |
| A reset runs while a payment is executing, or two resets run at once | `WalletGate` (a singleton): payments enter shared, a reset enters exclusive, waits for payments inside to leave and holds new ones back until it is done. Entered before any database transaction opens, released in `finally`; fault delays are outside it, so a hanging request never blocks a reset | Milestone 2, src/Wallet.MockApi/Services/WalletGate.cs, TransactionService.cs, Endpoints/AdminEndpoints.cs | review only |
| The caller disconnects during an injected delay | Delays honour the request's cancellation token. Before execute nothing has been written; after execute the transaction is already committed, the cancelled wait is swallowed and the stored result stands, found by its key | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.TimeoutAfterExecuteIsFoundByKeyWhileTheRequestStillHangs (opt-in SQL) |
| Admin endpoints reachable without a key outside Development | With no `Wallet:AdminKey`, `/admin` routes are open in Development only and return 403 `admin_key_required` elsewhere; with a key, the `X-Wallet-Admin-Key` header must match (constant-time compare) | Milestone 2, src/Wallet.MockApi/AdminKeyFilter.cs | FaultTests.AdminKeyRequiredWhenConfigured (opt-in SQL) |
| A fault set with `once` is seen by two concurrent payments | `FaultSwitch.Take` reads and clears under one lock, so only one payment gets it | Milestone 2, src/Wallet.MockApi/Services/FaultSwitch.cs | FaultTests.OnceFaultClearsAfterOneRequest (opt-in SQL; sequential) |
| Wallet returns an error on execute (fault `error`) | 500 `injected_error` before anything is written; the key stays unknown (by-key 404), so a retry with the same key executes normally | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs and FaultSwitch.cs; agent-side handling in milestone 3 | FaultTests.ErrorFaultReturns500AndMovesNothing, OnceFaultClearsAfterOneRequest (opt-in SQL) |
| Wallet answers slowly (fault `slow`) | The execute waits `delayMs`, then runs normally and returns 201 | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.SlowFaultDelaysButSucceeds (opt-in SQL) |
| Wallet times out before execute (fault `timeoutBeforeExecute`) | Waits `delayMs`, then 504 `injected_timeout`; nothing is written and by-key is 404 `unknown_key`, so the outcome is known: not done | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | FaultTests.TimeoutBeforeExecuteMovesNothingAndByKeyIs404 (opt-in SQL) |
| Wallet times out after execute (fault `timeoutAfterExecute`), wallet side | The payment commits first, then the response is held for `delayMs`; `GET /transactions/by-key/{key}` already returns the `done` row while the request hangs | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs and Endpoints/TransactionEndpoints.cs | FaultTests.TimeoutAfterExecuteIsFoundByKeyWhileTheRequestStillHangs (opt-in SQL) |
| PIN entered wrong repeatedly | Each wrong PIN is 422 `pin_invalid` with `attemptsLeft`; after `Wallet:MaxPinAttempts` the PIN is locked and every payment that checks it is 423 `pin_locked`, even with the right PIN, until `POST /admin/reset`. Nothing moves; the PIN is never echoed or logged | Milestone 2, src/Wallet.MockApi/Services/TransactionService.cs | TransactionTests.ThreeWrongPinsLockTheUser (opt-in SQL) |
| Payment larger than the balance | The quote reports `sufficient: false` but does not refuse; the execute's conditional debit finds no row, the transaction is stored as Failed `insufficient_funds` and 422 is returned. Nothing moves | Milestone 2, src/Wallet.MockApi/Services/PaymentValidator.cs and TransactionService.cs | TransactionTests.InsufficientFundsIs422AndNothingMoves (opt-in SQL) |
| Two opposite-direction transfers deadlock on the account rows | SQL Server kills one (error 1205); it surfaces as 500 with nothing committed; a retry with the same key executes | Milestone 2 TransactionService; agent-side retry in milestone 3 | review only (not reproduced; documented from the lock order) |
