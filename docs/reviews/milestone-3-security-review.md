## Important
**I1. A settle can mark a PIN payment NotDone while the original call is still running, and then the original moves the money (rule 6).** `ConfirmHandler.cs:150-175` (settle sends `pin: null`, then `CompleteRefusedAsync` on any refusal); wallet `TransactionService.cs:79-95, 128-138, 161-168, 355-360`. The wallet stores nothing under a key until `RunAsync` inserts the row; validator and PIN refusals are returned, not stored. A request queued behind a `slow` fault (or inside the PBKDF2 check) still runs after the client gave up. Sequence: Confirm with PIN times out → Checking; settle resends without a PIN; the key is still unknown, so the wallet answers 422 `pin_required`; the agent completes NotDone `not_done_nothing_taken`; then the original commits and the money moves. Fix before milestone 4 adds a settle trigger: in the settle treat `pin_required`, `pin_malformed`, `pin_invalid` and `pin_locked` as still Checking, never final; more generally finalise NotDone from a settle only on a stored failure, or when the record is older than a configured settle window (wallet timeout plus the longest fault delay; a setting shown in settings); add a failure-modes row and a test (slow fault, PIN payment, settle during the delay → Checking, then Done). https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults

**I2. A record can be stranded in Executing for good, with no path to Checking (rule 6).** `ConfirmHandler.cs:61-142`, `PendingStore.cs:206-240`. Any non-cancellation exception during the recheck or execute (an unexpected exception from `ReadFromJsonAsync`, a `SqlException`/`DbUpdateException` writing the outcome after a Done execute), a process restart between `TryBeginExecute` and the outcome write, or a cancellation landing inside `CommitAsync` of `TryBeginExecuteAsync` leaves Executing; `SettleCheckingAsync` accepts only Checking, `ExpireAllOpenAsync` skips Executing, `ExpireDueAsync` handles Pending only. Money may have moved and the card never reaches Checking or Done. Fix before the screen shows card states: a sweep `MarkStaleExecutingAsync(olderThan)` (start and on the expiry timer) moving Executing older than `WalletTimeoutSeconds` plus a margin to Checking (never NotDone; needs an `ExecutingSince` column; `CanLeave` already allows Executing → Checking); a catch-all around the execute section that moves the record to Checking and rethrows; a failure-modes row. https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services

**I3. `ParsedRequest` is not validated as untrusted output, and some of its text already reaches replies and the audit (rules 2, 3, 4).** `Orchestrator.cs:88-93`: `UnsupportedReason` is free text and goes into the audit `Reason` column (`nvarchar(100)`; a longer value throws `DbUpdateException` out of `HandleAsync`) and into `AgentReply.Unsupported`; `:172` echoes `RecipientText` as `Refusal.Detail`; `:126-135` uses any 7+ digit `RecipientText` as a phone, so a number the model invented becomes a card recipient; `BillerCode` and `ProductType` are not checked against their sets; no string has a length limit; `EditDistance` is O(n·m) on whatever length arrives. Today nothing reaches a wallet write unvalidated. Fix before milestone 6: a `ParsedRequestValidator` before `HandleAsync` (fixed sets for `UnsupportedReason`, `BillerCode`, `ProductType`; text ≤ 100 chars; `ProductValue > 0`; `AmountValue` within the caps; defined enum values); accept a phone only by un-masking a token from this message's mask map; echo `RecipientText` only when it is a substring of the user's original message, or drop the detail.

**I4. The rule 1 test proves "only ConfirmHandler calls `ExecuteAsync`", not "only a tap reaches money".** `NoTapNoMoneyTests.cs:45-67`. Blind spots: callers of `ConfirmAsync`/`SettleCheckingAsync` are not checked (a parse path calling `ConfirmAsync` on a typed "yes" would pass); a second HTTP path to `POST transactions` is not checked; reflection is not checked; only Agent.Core is scanned. Fix with the first caller in milestone 4: extend the scan to Agent.Web and assert `ConfirmAsync` is referenced only by the card component's Confirm click handler and `SettleCheckingAsync` only by that handler or the settle timer; assert the literal `"transactions"` appears only in `WalletClient.ExecuteAsync`; assert no Agent.* assembly reflects on `WalletClient`.

## Minor
**M1.** Concurrent settles, or a reset between the re-read and the write, throw instead of returning AlreadyHandled (`ConfirmHandler.cs:162-174`, `PendingStore.cs:159-181`); in Blazor Server an unhandled exception ends the circuit. Fix: `CompleteAsync` returns a `TransitionResult` and the handler maps "already left" to `AlreadyHandled`.
**M2.** The daily cap is check-then-act across cards (`Checks.cs:89-108`, `ConfirmHandler.cs:245-254`): two cards confirmed together both pass; the wallet does not enforce the cap; history is one page of 200. Fix: serialise Confirm per user (`sp_getapplock` in the begin-execute transaction, or a per-user semaphore) and count today's Executing and Checking records as spent.
**M3.** The client key is an endpoint filter, not authentication: it runs after parameter binding (a caller without the key still makes the wallet bind the body; in Development a bad body gives 500); in Development with no key any non-empty value is accepted from any host that can reach the port. Fix: an authentication handler on the group (`RequireAuthorization`), and document "never bind beyond loopback without `Wallet:ClientKey`". https://learn.microsoft.com/en-us/aspnet/core/security/authentication/
**M4.** Confirm and settle take only a pending id (`ConfirmHandler.cs:58, 150`); authorisation rests on the screen alone. Fix: pass `userId` from the session and add `p.UserId == userId` to the conditional updates and finds; cheap now, harder after milestone 4.
**M5.** `Agent:WalletBaseUrl` accepts any scheme and host; the client key travels in a header over plain HTTP. Fix: outside Development require `https` or a loopback address.
**M6.** Normalisation keeps Unicode format characters (`ArabicText.cs:95-129`): zero-width and bidi controls are kept, so a typed name with a zero-width joiner fails to match, and a saved or registered name with U+202E can visually reorder text on the card (payee spoofing; Razor encoding does not neutralise it). Fix: strip `UnicodeCategory.Format` in `NormalizeLetters`; render names inside `<bdi>` or `dir="auto"` on the card.
