## Important
**I1. Concurrent PIN guesses bypass the lockout (rule D8).** `TransactionService.cs:127-166`: the lock flag is read before the slow PBKDF2 check and the counter is increased after it, so many simultaneous requests all see `PinLocked = false`; the number of guesses is bounded by concurrency, not `MaxPinAttempts`; a correct guess resets the counter and proceeds even if others locked the PIN meanwhile. The PIN space is 10^4 and the PIN is the only control above 1,000,000 IQD; `failure-modes.md:30` and `wallet-api.md:272` claim a lockout the code does not guarantee; `ThreeWrongPinsLockTheUser` is sequential. Fix: reserve an attempt before verifying (one conditional `ExecuteUpdate` on `!PinLocked` that increments and sets the lock when the limit is reached; zero rows → refuse), verify, reset on success; add a test with about 20 concurrent wrong PINs plus the right one asserting at most `MaxPinAttempts` checks counted and 423. https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-configuration#lockout, https://learn.microsoft.com/en-us/ef/core/saving/concurrency

**I2. The contract implies a by-key 404 is final; it is not (rule 6).** `wallet-api.md:224, 264, 296`, `failure-modes.md:23, 27`. A 404 means the key has not been written yet: with `slow` the delay precedes the insert; a request held in transit behaves the same. A client that times out, sees 404 and marks Failed breaks rule 6 when the money then moves. Fix (docs): a 404 is final only after the original call has definitely ended; the safe way to settle Checking is to resend the same body with the same key (runs once or replays; 409 means keep checking); add a failure-modes row for "slow fault longer than the client timeout: by-key 404, then done". https://learn.microsoft.com/en-us/azure/architecture/best-practices/transient-faults

**I3. `POST /transactions` and every read endpoint have no caller check; `userId` comes from the body (rule 1).** Anything reaching port 5276 can move money for any user up to the PIN threshold and read any balance, history or purchase code. Deferral to milestone 3 accepted with conditions: Kestrel bound to localhost; synthetic data; the only legitimate client does not exist yet; `AllowedHosts` is not access control (a remote caller can send `Host: localhost` if the port is exposed); browsers cannot POST cross-origin because the custom `Idempotency-Key` header forces a failing preflight (keep it that way). Fix in milestone 3 before the client is merged and before any hosted demo: one shared-secret filter (`X-Wallet-Client-Key`, pattern of `AdminKeyFilter`) on a group covering all routes except `/health`; key in user secrets for both apps, validated on start; no-key mode only on a loopback bind in Development. https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/min-api-filters, https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets

**I4. A replay ignores who is asking and what was asked (rules 5 and 6).** Any body, even an invalid one, with a known key returns that key's full response (balance, purchase code); a different `userId`, amount or recipient under the same key gets the first outcome back with 200. Under the current trust model it is not a new disclosure (I3), and rule 5 is about the model, so the rule-5 duty sits with the client. The integrity risk is real: if the agent ever reuses a key for a different pending record, the wallet reports Done with another payment's figures. Fix in milestone 3 with I3: store a request fingerprint (userId, type, amount, recipient, bill or product) on the row; on mismatch return 422 `idempotency_key_reused` without the stored body; require `userId` on by-key and 404 when it does not match. (The IETF Idempotency-Key draft prescribes 422 on reuse with a different body.)

## Minor
**M1.** Idempotency keys are case-insensitive under the default collation (`WalletDbContext.cs:127-128`, migration `nvarchar(64)`): `AbC` and `abc` are one key. Fix: binary collation on the column, or reject keys not matching `^[A-Za-z0-9_-]{1,64}$` with 400; milestone 3 uses `Guid.NewGuid().ToString("N")`. https://learn.microsoft.com/en-us/ef/core/miscellaneous/collations-and-case-sensitivity
**M2.** In Development with no admin key, `POST /admin/reset` takes no body, so a web page on the demo machine can trigger it with a non-preflighted `fetch` (`AdminKeyFilter.cs:23-26`, `AdminEndpoints.cs:40`); `/admin/faults` needs JSON so it gets 415. Fix: always require a custom header on `/admin` so browsers must preflight; better, set an admin key for every demo run. A hosted demo must not run as Development, must set `Wallet:AdminKey` (16+ chars) and must have the I3 client key. https://learn.microsoft.com/en-us/aspnet/core/security/cors
**M3.** Every ordinary retry of a done key passes validation, inserts and hits 2601, which EF logs at Error with the key in the SQL message (`TransactionService.cs:98-113, 191-202`). Fix: `LoadAsync(key)` at the start of `ExecuteCoreAsync` and replay at once; keep the 2601 catch for the real race. Also simplifies I1.
**M4.** Opposite-direction transfers can deadlock (`TransactionService.cs:208-219`; documented `failure-modes.md:32`); victim rolls back fully, 500 without `code`, same-key retry safe. Fix: lock both account rows in ascending id order before the debit, or catch 1205 and retry once with the same key. https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide
**M5.** Reset runs synchronous database I/O and 12 PBKDF2 hashes inside an async handler (`AdminEndpoints.cs:66`, `SeedReset.cs:13-41`). Fix: `ResetAsync`/`ApplyAsync`. https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices#avoid-blocking-calls
**M6.** A reset during a hanging `timeoutAfterExecute` leaves the client holding a 201 for a row the reset wiped; with `slow` the payment runs against the fresh seed after the reset. No money corruption. Fix: failure-modes row; in milestone 3 the agent's reset expires its pending and Checking records; optionally a wallet reset counter (Khalil decides).
**M7.** Admin key has no minimum length (`WalletOptions.cs:35`); "closed outside Development" untested. Fix: `[MinLength(16)]`; a `UseEnvironment("Production")` test expecting 403 on all three `/admin` routes.
