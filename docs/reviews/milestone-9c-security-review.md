## Findings

### Minor

**M1. An exception on the part running in `SendAsync`, `TapOptionAsync`, `DeclineQuestionAsync` or `GiveConsentAsync` leaves the queued parts in place; they can run later under an unrelated reissued card.**
- Where: `src/Agent.Core/Conversation/Conversation.cs` lines 277-280 (`SendAsync` catch: `Failed(ex)` only), 527-530, 594-597, 692-695 (the same shape); contrast `AdvanceAsync` lines 1331-1335, whose catch marks the part finished and runs the next. The `ReissueAsync` comment (line 836, "the queue is always empty by then") and `docs/agent-core.md` assume no stale queue.
- What: a compound message is read while an older card is Done (not live, so nothing is cancelled); `DropQueue()`/`QueueParts()` (lines 457-460) queue part 2; `HandleCoreAsync` for part 1 throws before its last line (a scope that fails to build, a `Changed` handler that throws); the catch shows `not_done_nothing_taken` and returns with part 2 still queued and `QueuedRequests` 1. The user taps Send again on the old Done card: `ReissueAsync` passes (no question, state Done), a new card is shown; on its Confirm, `ShowOutcome` sets `partFinished = true` (line 1734) and `AdvanceAsync` dequeues and runs part 2, a part of a message that had failed. No rule is broken (part 2 only becomes a card that waits for its own tap), but the card is unexpected, the trace panel shows a stale count until the next message, and that message's `requests_dropped` reports parts that belonged to a failed message. Needs an exception, not a wallet refusal (those are `Unavailable` results), so it is rare.
- Fix: choose one policy for an exception on part 1 and apply it in the four catches: either `DropQueue()` (traces `requests_dropped`; the message is over) or, as `AdvanceAsync` already does for a later part, `partFinished = true; await AdvanceAsync(token);`. Fix the `ReissueAsync` comment and the doc line to say which. One test with a scope factory that throws on the orchestrator's scope for the first part of a two-part message, asserting `QueuedRequests == 0` afterwards (or the second card, under the other policy).

**M2. `suppressLearningRow` spans the advance: a four-to-six-digit answer to part 1's typed question suppresses the learning rows of every part that runs on in the same action, and the `more_than_three_requests` row, although those rows are written under the compound message's masked text, not the digits.**
- Where: `Conversation.cs` line 301 (set for the whole `SendAsync`), line 287 (cleared in `finally`), lines 1470-1475 (`WriteLearningAsync` returns early and nulls `LastLearningEntry`), line 1326 (`AdvanceAsync` switches `lastMaskedText` to `queuedMaskedText` but leaves the flag).
- What: "send to my brother, and twenty-five thousand to <unknown name>": part 1 asks `which_amount`; the user types `900000` (six digits, `DigitsOnly` true); the code reads it, part 1 is refused `insufficient_balance` (correctly without a row: the message may be a PIN); the refusal finishes the part, part 2 runs in the same `SendAsync` and is refused `recipient_not_found`, and its row, under the masked compound message, is not written; `LastLearningEntry` is null, so the runner grades no entry. The same for the `more_than_three_requests` row when the cap reply follows. Learning data only; nothing sensitive.
- Fix: in `AdvanceAsync`, after `lastMaskedText = queuedMaskedText;` set `suppressLearningRow = false;` (the text now logged is the compound message's), and the same in `ShowNotPreparedAsync`; one test on the scenario above asserting the `recipient_not_found` row exists.

**M3. `ConfirmAsync` and `SettleAsync` now run the orchestrator, the learning write and the "not prepared" message after the outcome, but, alone among the actions, have no general catch: a throw from `ShowNotPreparedAsync` or from a `Changed` handler escapes to the Blazor event handler and ends the circuit.**
- Where: `Conversation.cs` lines 714-751 and 757-794 (the outer try has only the `OperationCanceledException` catch; the handler call is wrapped at 726-736, and `AdvanceAsync` wraps `HandleCoreAsync` only, lines 1327-1335, not `ShowNotPreparedAsync` at line 1320); the session's `Localise` runs inside `Add` → `Changed` (`ChatSession.cs` lines 388-392, 473-477, 611-618), where `Text("List_joiner", joined, name)` and `Text("Refusal_not_prepared", names)` are `string.Format` calls over the two keys Khalil is about to write.
- What: a `{2}` or an unbalanced brace in `Refusal_not_prepared` or `List_joiner` throws `FormatException` on the third Confirm of CMP-07, inside `ConfirmAsync`, after the payment is Done; `CardPanel.ConfirmAsync` has no try, so per Microsoft's Blazor guidance the unhandled exception in the event handler is fatal to the circuit (learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/handle-errors, "Unhandled exceptions ... in event handlers"). Money is unaffected (the outcome is already shown and the record Done), but the console dies mid-demo on the one flow that shows rule 22.
- Fix: give `ConfirmAsync` and `SettleAsync` the general catch the other actions have (`catch (Exception ex) when (ex is not OperationCanceledException) { Failed(ex); return null; }` on the outer try, after the outcome is shown, is safe: the handler call keeps its own catch and `ShowAfterExceptionAsync`), and add to `PhoneStringsTests` a check that every value holding `{` formats with dummy arguments without throwing, so a wording slip is caught at test time rather than on the phone.

## Recommendations

- **R1.** `QueueParts` names every part beyond the cap (line 1395, `Skip(partsKept)`), so the length of the second line is bounded only by what the parser returns: the candidate's `MaxOutputTokens` (1500 in both `appsettings.json`) allows roughly twenty to twenty-five entries, each named by its text or `Type_request`. The validator checks the whole list first, which is cheap at that size, and the trace and the learning row carry counts only, so there is no exhaustion risk today; but a model that pads the list with `unclear` entries would put twenty "request" words on the phone. Consider naming at most `MaxRequestsPerMessage` parts (or a fixed few) and letting the learning detail keep the full count; the wording of "and N more" would be Khalil's.
- **R2.** Ruling 5 (as the plan states, "merged or not") drops the queue on the merge path too: when a typed answer to a typed question cannot be read in code and the model reads it as a partial transfer, `DropQueue()` (line 457) has already dropped the other parts before `MergePartial` keeps the pending request, and the phone says nothing (only `requests_dropped` is traced). The user who answered "about twenty-five" to `which_amount` loses part 2 silently, while a user who answered "25000" keeps it (`AnAnswerReadInCodeKeepsTheQueue`). Khalil's call: keep the queue when the parse merges (one condition before line 457), or a phone line for a drop (new key, his wording).
- **R3.** The not-prepared names are shown as typed, with no digit conversion: a transfer part whose recipient was a typed number (un-masked at line 1391, found verbatim at line 1398) shows that number in the digit form the user typed, while every other figure and the card's `DisplayName` go through `PhoneFormat.Digits` (`CardPanel.razor` line 15). Apply `PhoneFormat.Digits` to each name in `ChatSession.NotPreparedNames` (line 613) so the phone frame keeps Arabic-Indic digits throughout, as the layout rule says.
- **R4.** `RejectsTap` checks the id only, so a Confirm with the matching id on a card that is Done, Cancelled or Expired still reaches `ConfirmHandler.ConfirmAsync` (lines 720-730) and gets its answer from the record's state. This is the pre-9c behaviour, rule 6 makes it safe, the phone's button is disabled unless live, and the runner's `twice` on a single-card case relies on it; optionally answer `already_handled` in the conversation for a card in a finished state and keep the handler for Live and Checking, which also saves a scope per stale tap.
- **R5.** Ruling 1 writes the `more_than_three_requests` row only when the last prepared part finishes, so a user who abandons the prepared cards leaves no row, and the tuning data never learns that the model split that message into four (`requests_split` in the trace is the only record). The reply's timing is the ruling; the row could be written at the split instead, with the reply still at the end. Khalil's call, since the row is one of the graded learning-log reasons.
- **R6.** The plan's Task 2 step 3 names `TraceSinkTests` for the three new step names, but no test walks `TraceSteps`; the names are pinned by `ConversationCompoundTests` through the constants, which is enough. If a list of steps-with-count-details is ever added to `TraceSinkTests.NoPinKeyCodeOrPhoneInAnyStep`, add `requests_split`, `next_request`, `requests_dropped` and `tap_rejected` to it.
