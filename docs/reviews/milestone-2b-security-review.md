## Important
**I1. `POST /users/{id}/consent` lets any caller, including any web page in the demo browser, grant the D22 consent for any user; this range makes the milestone 2 I3 worse.** `ReadEndpoints.cs:32-34, 78-86`. The route takes no body and no custom header, so a cross-origin `fetch(url, {method:'POST', mode:'no-cors'})` is a CORS "simple request": the browser sends it without a preflight; the response is opaque, but the write happens. Inconsistent with the admin routes, where the milestone 2 M2 was closed by requiring a custom header (`failure-modes.md:24`). Effect: U5's first-use consent screen (D2, D22, "never cut: consent screen") can be bypassed; there is no revoke route, so only a reset undoes it. Not a new data disclosure: `GET /users/{id}/balance` does not check consent and is already open under I3; the harm is to the integrity of the consent record. Fix, before the milestone 3 client is merged or any hosted demo: put the route under the I3 client-key filter (`X-Wallet-Client-Key`, a custom header, so browsers must preflight); cheap interim: require a JSON body (`application/json` forces a preflight) or the "header present" rule `/admin` uses in Development; add a failure-modes row; in milestone 3 make the consent handler the only caller and add an architecture test, mirroring rule 1. https://learn.microsoft.com/en-us/aspnet/core/security/cors#preflight-requests, https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery, https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/min-api-filters

**I2. An untracked second copy of the held-out set sits inside the repository (rule 7).** `git status` shows `docs/zaincash-testdata-export-v0.15/` as untracked (file names listed only). It contains `testdata/requests.heldout.jsonl`, `requests.dev.jsonl`, a second copy of the eight seed files and `docs/matching-rules.md`. Risks: a `git add -A` or `git add docs` commits a duplicate of the sealed file; any repository-wide search by an agent or a reviewer would print held-out content; the duplicate seed files are an unhashed second source that can drift from `data/seed`. Fix, before the next commit: move the folder outside the repository or delete it now that `data/` holds the export; if it must stay, add it to `.gitignore`. Not in the commit range, but area 7 asks for it.

## Minor
**M1. `GET /accounts/by-phone/{phone}` is a name-and-status oracle for every account** (`ReadEndpoints.cs:36-38, 88-100`): registered name and status for any number, users' own accounts included; numbers are sequential, so enumeration is trivial. Under I3 every read is already open, so this is incremental; once I3 is fixed, the agent itself becomes the oracle (D16, confirmation-of-payee pattern). Fix: in milestone 3/7, rate-limit typed-number lookups per session in Agent.Web with `Microsoft.AspNetCore.RateLimiting`, and keep the registered name out of the model (rule 5). https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit
**M2. Gaps at the seed input boundary.** (a) `RespectNullableAnnotations` does not cover collection elements, so `[null]` in `users.json` gives a null item and `Validate` throws `NullReferenceException`, not `SeedException`; same for `string[] CheckOrder`. (b) `IOException` and `UnauthorizedAccessException` from `File.ReadAllBytes` (`SeedSet.cs:102`) are not wrapped and surface raw with the full path; `migrate` (`Program.cs:64-73`) catches neither. (c) Checks the database enforces but the loader does not: column lengths (Phone 15, codes 8/16, names and aliases 100, label 50), uniqueness of `users[].number`. A future export with a long alias fails at `SaveChanges`: in `migrate` an unhandled `DbUpdateException`, in reset a 500 with no `code` (transaction rolls back, no half seed). Fix: reject null elements, validate lengths from the same constants as `WalletDbContext`, wrap `IOException`, catch `DbUpdateException` in `migrate`. https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/nullable-annotations
**M3. The payer account's status and the one-default-per-user invariant are enforced only by a test on today's files.** `PaymentValidator.cs:123-128`, `WalletDbContext.cs:54-70`, `SeedSet.cs:154-162`. `PaymentValidator` never checks the payer's own `Status`; `SeedSet.Validate` does not require user accounts to be `active`; nothing in the database prevents two `IsDefault` accounts for one user (`SingleOrDefaultAsync` would then throw: 500 without `code` on quote, execute and balance). Fix: add the active-user-account rule to `Validate`; refuse a closed payer with `account_closed` (wording is Khalil's); add `HasIndex(a => a.UserId).IsUnique().HasFilter("[IsDefault] = 1")`. https://learn.microsoft.com/en-us/ef/core/modeling/indexes#index-filter
**M4. Seeded idempotency keys and purchase codes are predictable.** `SeedData.cs:20, 44-48, 182`: `seed-H0001`..`seed-H0086` pass the client key regex, so any caller can replay or look up a seeded row, purchase code included; order codes `9` + zero-padded history digits are derivable. Not new disclosure under I3; with I4 unfixed, a client that ever sends a `seed-` key gets another payment's Done outcome. Fix: reject client keys starting with `seed-` (400 `invalid_idempotency_key`), or fold into the milestone 3 fingerprint work; document that seeded codes are display-only.
**M5. `AdoptTestSeed.Down` cannot run on a seeded database, and the wipe is documented in only one place.** `AdoptTestSeed.cs:291-299`: `Down` alters `Accounts.UserId` to NOT NULL with default 0, which fails while the 37 non-user accounts hold NULL. `Up` deletes every row in whatever database the `Wallet` string points to; documented in `data/seed/README.md:97` and the migration comment, not in `README.md`'s database section. Fix: one README line; make `Down` delete rows first or document it as unsupported. https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/managing#adding-raw-sql
**M6. `Wallet:SeedDirectory` resolves a relative path against the working directory, not the content root** (`WalletOptions.cs:56-57`, `SeedSet.cs:96`). `[Required]` accepts `"seed"`, which means different folders under `dotnet run`, `dotnet test` and a service host. Fix: validate `Path.IsPathRooted`, or resolve against `IHostEnvironment.ContentRootPath` in `PostConfigure`. https://learn.microsoft.com/en-us/dotnet/core/extensions/options#options-validation
