## Findings

### Minor

**M1. `Conversation.ListAliasesAsync` has no general catch, and both panels call it from `OnInitializedAsync` and from a discarded `InvokeAsync` without one; an exception there is fatal to the circuit.**
- Where: `src/Agent.Core/Conversation/Conversation.cs` lines 815-833 (`ListAliasesAsync` catches only `OperationCanceledException`; contrast `DirectoryAsync` line 867, which catches `Exception` and traces `error`, and `SaveAliasAsync` line 801); `src/Agent.Web/Components/Phone/DirectoryPanel.razor` lines 94 and 109-113 (`LoadAsync` with no try/catch); `src/Agent.Web/Components/Console/AliasesPanel.razor` lines 95 and 110-116.
- What: `WalletClient.GetContactsAsync` itself never throws, but `scopes.CreateAsyncScope()` and `GetRequiredService<AliasDirectory>()` can (an `ObjectDisposedException` when the circuit's provider is torn down while a reload is queued, or any DI failure). Per Microsoft's Blazor error-handling guidance an unhandled exception in `OnInitializedAsync` or in an event handler ends the circuit (learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/handle-errors#component-initialization-methods). The exception also escapes before `Release()`? No: `finally` releases the gate, so the conversation is not wedged, but the circuit is lost and the console dies mid-demo.
- Fix: in `ListAliasesAsync` add `catch (Exception ex) when (ex is not OperationCanceledException) { trace.Record(TraceZone.Code, "error", ex.GetType().Name); return new WalletResult<WalletContacts>.Unavailable("error"); }` as `DirectoryAsync` does; in both panels wrap the body of `LoadAsync` in a try/catch that sets `contacts` to an `Unavailable` result (never `ex.Message`). One test: a scope factory that throws on `CreateAsyncScope` gives `Unavailable` and a traced `error`.

**M2. `TraceSteps.AliasOffered` documents a detail the code never writes.**
- Where: `src/Agent.Core/Trace/TraceSteps.cs` line 27 ("The detail is an account id or a code") and line 29 ("the detail is the account id"); `Conversation.OfferAlias` line 1472 traces `null`; `ConversationAliasTests.AMB19OffersTheAliasAfterTheDonePaymentAndTheSecondRequestAsksAgain` pins `e.Detail is null`.
- What: a later reader (or a grader of the trace) expects an id that is not there; the plan's ruling 6 names the step only, so the code is right and the comment is wrong.
- Fix: change the two comments to "no detail" (or trace the account id as `alias_saved` does, and update the test); either is a one-line change.

**M3. `AliasDirectory.SaveForPhoneAsync` validates the text only after two wallet round trips; `SaveAsync` validates first.**
- Where: `src/Agent.Core/Aliases/AliasDirectory.cs` line 110 (`TryValidate` after `GetUserAsync` line 82 and `GetAccountByPhoneAsync` line 95); contrast `SaveAsync` line 52.
- What: a blank, over-long or number-like text typed with a number in the phone directory costs two wallet reads before `alias_invalid`, and with the wallet down it answers `Unavailable` (`not_done_nothing_taken`) instead of the refusal the text deserves. Pure validation before I/O is the pattern the rest of the agent follows (`Orchestrator.TransferAsync` refuses `invalid_number` before any read).
- Fix: move the `TryValidate` block to just after `TryNormalize` (line 79), so the order is number format, text, own number, wallet. `AliasDirectoryTests.ABlankATooLongAndANumberLikeTextAreRefusedAliasInvalid` can gain a phone-path case.

**M4. `DirectoryPanel.Show` has a dead `text` parameter.**
- Where: `src/Agent.Web/Components/Phone/DirectoryPanel.razor` line 153 (`private void Show(AliasResult? result, string? text)`); callers at lines 136 (`Show(result, text)`) and 150 (`Show(..., null)`). The body reads `saved.Alias.Text` (the wallet's stored, trimmed text, which is the right source) and never `text`.
- What: no behaviour problem; dead code that suggests the typed text might be shown untrimmed. Fix: drop the parameter and the local `var text = aliasText;` at line 132.

**M5. Every directory save or delete reloads the list twice, each reload taking the conversation's turn and toggling `Busy` on the phone.**
- Where: `src/Agent.Web/Components/Console/AliasesPanel.razor` lines 100-110 (`OnSessionChanged` queues `InvokeAsync(LoadAsync)` on a new `WalletVersion`) and lines 142 and 148 (`SaveAsync` / `DeleteAsync` also `await LoadAsync()`); the same shape in `DirectoryPanel.razor` lines 104-110, 144 and 150.
- What: `Conversation.DirectoryAsync` raises `WalletVersion` and `Changed` before it returns, so the version handler already reloads; the explicit reload is a second `ListAliasesAsync`, serialised behind the first by the gate. Bounded (two, not a loop), but each `ListAliasesAsync` sets `Busy` and raises `Changed`, re-rendering every phone component and disabling the Send button while a console panel refreshes. Microsoft's guidance is to avoid redundant renders and awaits in event handlers (learn.microsoft.com/en-us/aspnet/core/blazor/performance/rendering).
- Fix: remove the trailing `await LoadAsync()` from `SaveAsync` and `DeleteAsync` in both panels (a refusal changes nothing to reload; a save or delete is reloaded by the version handler). Optionally make `ListAliasesAsync` not set `Busy` (it is a read), as `RefreshAsync` does.

## Recommendations

- **R1.** `Conversation.SaveAliasAsync` line 801: the generic catch calls `Failed(ex)` after `ClearAliasOffer()`, so an unexpected exception loses the offer and shows `not_done_nothing_taken`, while a wallet `Unavailable` keeps the offer open for another tap (lines 789-794). `AliasDirectory` promises not to throw, so this is only the last resort; still, restore the offer in the catch as the `Unavailable` branch does, so the two "nothing written" paths behave the same.
- **R2.** `AliasDirectory.SaveAsync` line 62 and `SaveForPhoneAsync` line 95 accept a closed target account (`WalletContact.AccountStatus` / `WalletAccount.Status` are not read), and `docs/wallet-api.md` says so explicitly ("active or closed"). No money risk: a transfer to such an alias is refused `account_closed` by `Orchestrator.TransferAsync` (line 400 reads `chosen.AccountStatus`). But the directory lets the user save a name that can never be paid and tells them nothing. Khalil's call: refuse `account_closed` in the directory, or show the status in the list.
- **R3.** The own-number guard (`SaveForPhoneAsync` line 84) compares the user's `WalletUser.Phone` only, and `GET /accounts/by-phone` (`AccountSummary`) exposes no owner, so a number of another account the same user owns could be aliased; the wallet's `same_account` (`PaymentValidator.cs` line 197) catches only the default account. Pre-existing for typed numbers (not introduced by 9a) and harmless under the demo seed; if a user ever has two accounts, add `userId` to `AccountSummary` or a `same_user` refusal. A wallet contract change, so Khalil's decision.
- **R4.** Ruling 4 refuses only an exact key clash. The directory therefore still lets a user save a bare first name that is a word of several saved names (rule 15 would have asked; the alias now goes straight to the card). D15 says a bare name shared by several is never *offered*, and the directory is the user's explicit choice, so this is by design, but it is not written anywhere. Add a line to `docs/agent-core.md` "Known limits" and a `docs/failure-modes.md` row (the registered name on the card is the guard, as for R2), and let Khalil decide whether the directory should refuse or warn.
- **R5.** `AliasEndpoints.IsUniqueViolation` (`src/Wallet.MockApi/Endpoints/AliasEndpoints.cs` lines 121-122, the 2601/2627 catch) is the last guard against a racing save and is reached by no test: every `AliasEndpointsTests` case is answered by the `AnyAsync` check at line 83 first. Add a test that posts the same text for the same user concurrently (for example eight `PostAsJsonAsync` tasks) and asserts exactly one 201 and the rest 409 `alias_exists`, so a change to the index or the catch fails the build.
- **R6.** `AliasOffer.RegisteredName` is carried from the orchestrator to the screen but unused: `ChatSession.Localise` formats `Offer_save_alias` with `offer.Text` only. D16's point is that the registered name is the one line the user did not write; showing it in the offer ("save X for <registered name>?") would let the user catch a wrong tap before saving. A resource-string change (`{1}`), so Khalil's wording; the code change is one argument.
