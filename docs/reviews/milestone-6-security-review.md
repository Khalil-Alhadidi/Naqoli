## Approved
- **Rule 9 (the key).** The key is read only from `Anthropic:ApiKey` or `ANTHROPIC_API_KEY` (`ParserFactory.ApiKey`). `MissingKeyMessage` and `ModelOptionsValidator` name settings, never a value. `ModelCandidate.ToString` and the settings component show no key. `ClaudeParser.ReasonOf` maps a failure to `http_NNN`, `connection` or the type name, and `ParserUnavailableException` carries no inner SDK exception, so neither its `Message` nor its `ToString` can echo the response body. `AnthropicAdapterTests.AnHttpFailureIsUnavailableWithTheStatusAndWithoutTheKey` checks `ex.ToString()` against a body that echoes the key, for 401, 400, 429, 500 and 529. The runner copies only `Anthropic:ApiKey` out of the web project's user secrets, only in Development, and only when the runner has no key of its own (`EvalCommand.cs` BuildHost). The web project's other secrets, including its database, never reach the runner. Neither the report settings nor the console lines include the key. `AnthropicClient` builds its own `HttpClient`, outside the factory's logging, so request headers are not logged.
- **Rule 2.** `ClaudeParser` passes no tools. It makes one `GetResponseAsync` per message, with the prompt as the system message. It asks for JSON-schema structured output: every object is closed, every field required, every enum fixed (`BuildSchema`). The reply is read with `JsonUnmappedMemberHandling.Disallow` and goes to `ParsedRequestValidator`. A truncated reply (`FinishReason.Length`) is `Unclear`/`truncated`. A bad reply never throws.
- **Validator against hostile output.** Enum strings must be exact, ordinal and lower case. Texts are capped at 100 characters. An amount must be finite, not below zero and below 1e28 (NaN and infinity are rejected). The product value must be above 0. A token not in the map is refused, and a recipient with a 7-or-more-digit run is refused. Overflow downstream is already safe: `AmountRule.TryWholeDinars` catches `OverflowException` on the million multiplier and checks against `long.MaxValue`. JSON that is not the structure becomes `Problem` `json`, including a fractional or huge `product_value` (a `JsonException`). `bill_label_text`, `operator_text` and `currency_text` are only matched against wallet data or refused, and never become a payee.
- **Rule 5 end to end.** `Conversation.SendAsync` masks before the parse call, and only a recipient that is exactly a token of this message's map is turned back into a number (`Unmask`). The trace holds `parse:<name>` and the intent, never the text. `OutboundPayloadTests.NothingFromTheWalletReachesTheModel` checks the whole payload, schema included, for seed phones, subscriber numbers, balances before and after each card, saved names, aliases, registered names and PINs. The prompt holds no seed data: "ياسر" is in no `data/seed/*.json`.
- **Prompt-injection posture.** The prompt says instructions in the message are the user's words. More to the point, nothing the model returns can act: the card is built by code, and only Confirm executes. `NoTapNoMoneyTests` is unchanged.
- **Learning log.** `LearningLog.WriteAsync` has no PIN, balance or code parameter (checked by a test). It masks both the detail and the text again before writing, then cuts them to the column lengths (100 and 1,000). The column lengths in the migration match the model. A failed write is traced with the exception type only. `ARecipientNotFoundReplyWritesOneRowWithMaskedTextAndNoPin` covers the card-PIN path.
- **Rule 6.** On a first execute, a 5xx that carries a wallet code becomes `Refused` and then NotDone `not_done_nothing_taken`. On a settle it stays Checking (`ConfirmHandler.cs` `Refused { Problem.Status: >= 500 }`), because the fault switch runs before the key lookup. A bare 5xx is still Unknown. The wallet's `UseExceptionHandler` sends ProblemDetails without `code`, so a real crash stays Unknown. Covered by `WalletErrorWithACodeIsNotDoneNothingTaken`, `WalletErrorOnASettleStaysChecking` and `ExecuteBareServerErrorIsUnknown`.
- **Timeouts and cancellation.** The linked CTS with `CancelAfter(TimeoutSeconds)` turns a timeout into `timeout`, and the caller's cancellation propagates (`TheCallersCancellationPropagates`). `LastUsage` uses `Volatile` reads and writes, and the parser is scoped (one per circuit, or per runner scope), so usage never crosses conversations. Logging uses source-generated `LoggerMessage` with the model id, numbers and the finish reason only.
- **Runner.** `StepErrorOf` keeps the type plus a fixed message (closes M1 of milestone 5). Report names carry `HHmm` (closes M2). The `--parser` value is checked against `^(scripted|claude:[a-z0-9_-]+)$`. The report holds ids, codes, model id, prompt version, tokens and cost. `RecordingParser` records the masked text (closes R3). No new code reads `requests.heldout.jsonl` outside `HeldOutGuard`.
- **Options.** `AgentOptions.Parser` is checked by regex. With `claude`, `ModelOptions` is validated at start, and `EvalCommand` catches `OptionsValidationException` and prints only the messages. With `scripted`, nothing of Anthropic is built. The disclosure lists Anthropic 12.56.0, Microsoft.Extensions.AI 10.11.0 and the three models. The repo never uses `ConfigureAwait`; the new code is consistent with that.
- **Regex safety.** In the `Masker` pattern (`Masker.cs:46`) the separator class `[ \-.]` and the digit class do not overlap, so backtracking is linear per start position. The `MaskMap` patterns have no nested quantifier. No ReDoS. Incoming messages are already capped by Blazor's 32 KB SignalR limit.

## Important
- **I1. The masker's idea of a number is narrower than the resolver's. Numbers can reach the model unmasked, and a number the model writes can pass the validator.**
  - **Files:** `src/Agent.Core/Masking/Masker.cs:46` (separators `[ \-.]` only), `src/Agent.Core/Parsing/ParsedRequestValidator.cs:140-143` (`RecipientIsSafe` uses `Masker.HasNumberRun`), against `src/Agent.Core/Text/PhoneNumbers.cs:53-63` (`StripSeparators` drops any `char.IsWhiteSpace` plus `( ) - .`) and `src/Agent.Core/Pipeline/Orchestrator.cs:161` (`PhoneNumbers.LooksLikeNumber` sends a recipient down the phone path).
  - **What:** `0770 123 4567` (non-breaking space, common when a number is pasted on a phone), tabs, line breaks, thin spaces, `(0770) (123) (4567)`, and groups split by bidi marks (U+200E, U+200F, U+061C) all have no run of 7 digits under the masker's rules. So: (a) the typed number goes to the model in clear (rule 5); (b) if the model writes such a string into `recipient_text`, `HasNumberRun` is false and the validator accepts it. The orchestrator then strips the separators, gets a valid `07…` number, and the card is built for a number the validator was meant to refuse ("the parse call invents a phone number", failure-modes line 18).
  - **Why it is not Critical:** money still needs the tap on a card built by code from the wallet's lookup. But two stated controls are bypassed, and the eval's `OutboundTextCheck.Normalize` would flag (a) only for seed numbers.
  - **Fix:** define one separator set and share it between `Masker` and `PhoneNumbers`. For example, separators `[\s\p{Cf}\-.()]` (note `\s` in .NET covers Unicode whitespace), keeping commas out for amounts. In the validator, refuse any non-token `recipient_text` for which `PhoneNumbers.LooksLikeNumber` is true. The guard then uses the same test as the code it protects. Add `MaskerTests` cases for NBSP, tab, newline, parentheses and LRM, and a validator test for each.
- **I2. A PIN typed into the chat reaches the model and the learning log, and the runner's PIN check does not look there.**
  - **Files:** `src/Agent.Core/Masking/Masker.cs` (`MinDigits = 7`, while wallet PINs are `^[0-9]{4,6}$`); `src/Agent.Core/Learning/LearningEntryRow.cs:5` (says rows hold "never … a PIN"); `src/Agent.Eval/Running/CaseDriver.cs:416-436` (`PinSeenAsync` scans messages, trace and `AuditEntries` only); `CaseDriver.cs:439-444` (`ResetAgentAsync` does not clear `LearningEntries`).
  - **What:** A user who types a PIN into the chat (a known user habit, and a `pin_in_chat_or_logs` expectation in the answer key) sends it unmasked to Anthropic. It is also stored in `LearningEntries.MaskedText` whenever the reply is a logged one, which is likely (`not_understood`). The grader cannot see either: the recorded parser texts and the learning rows are not scanned. Learning rows also pile up across cases and runs in `ZainCashAgent_Eval`.
  - **Why it matters:** the code comment promises something the code does not do, and the measured `pin_in_chat_or_logs` result can pass while the PIN sits in a stored table and in the model payload.
  - **Fix:** (1) Extend `PinSeenAsync` to `LearningEntries` (all text columns) and to `parser.Texts`, and clear `LearningEntries` in `ResetAgentAsync`. (2) Correct the comment in `LearningEntryRow`. (3) Add a failure-modes row. (4) The handling itself is Khalil's call. A 4–6 digit run cannot be told apart from an amount by shape, so options include: no learning row for a message whose only number run has 4–6 digits and no amount unit; a PIN-word check from the resource file; or accepting and documenting it.

## Minor
- **M1.** `src/Agent.Core/Wallet/WalletClient.cs:176-183`: any wallet `code` on a 5xx is a refusal. The ruling and the `ExecuteOutcome.Refused` doc name only `injected_error` and `injected_timeout`. Allow-list those two (`FaultErrors` codes) so a future 5xx carrying some other code keeps the rule 6 default (Unknown, then Checking) instead of finalising NotDone while the money may have moved.
- **M2.** `src/Agent.Core/Parsing/ParserFactory.cs:82`: production builds `new AnthropicClient { ApiKey = apiKey }` with the SDK's default retry policy. The tests set `MaxRetries = 0`, so the default is presumably non-zero. A 429, 5xx or 529 can then mean several HTTP requests for one message inside the 20 s timeout. That blurs "one parse call per message", the 429 failure mode and the cost record. Set retries explicitly (0, or a candidate setting shown in the settings component) and add a line to failure-modes.
- **M3.** `src/Agent.Core/Parsing/ClaudeParser.cs:179` with `ParseContext(string? PendingNote, MaskMap? Map = null)`: `ClaudeParser` sends whatever text it is given and falls back to `MaskMap.Empty` when the caller did not mask. Today only `Conversation` calls it, and it masks. As defence in depth, have `ClaudeParser` mask the text itself when `Map` is null, or refuse such a call, so a future caller cannot bypass rule 5.
- **M4.** `src/Agent.Core/Conversation/Conversation.cs` (SendAsync): no maximum length before the parse call. Each message up to the 32 KB SignalR limit is billed as input tokens, and there is no per-conversation rate limit. Suggest a `MaxMessageChars` setting (configuration, shown in the settings component) that refuses with `not_understood` before masking. This is a new setting, so it is Khalil's call.
- **M5.** `src/Agent.Core/Parsing/parse-prompt.md:31-38`: the three Arabic examples are copied verbatim from `docs/matching-rules.md` rules 8, 11 and 12, which come from the test-set workbook that also holds the held-out cases. I did not check them against the held-out set (rule 7). Khalil should confirm none of the three is a held-out message. If one is, that case is contaminated and its score inflated.

## Recommendations
- **R1.** `ClaudeParser.cs:51`: set `AllowDuplicateProperties = false` on `StrictJson` (new in System.Text.Json for .NET 10), so a reply that repeats `intent` is refused instead of last-wins.
- **R2.** `Masker.Mask`: a user who types the literal `<NUM_1>` produces a text where it cannot be told apart from a real token. The effect is limited to the user's own number, but escape or replace any typed `<NUM_` before masking.
- **R3.** `MaskMap.cs:57`: `^…$` also matches before a trailing `\n`. Use `\z`, as `PhoneNumbers` does. Harmless today because the validator trims first.
- **R4.** `EvalCommand.WebUserSecretsId` duplicates the GUID in `Agent.Web.csproj`. Add a test comparing it with `UserSecretsIdAttribute` on the Agent.Web assembly, so a regenerated id does not silently disconnect the runner from the key.
- **R5.** The learning log has no retention or review limit. It holds the user's masked words indefinitely with `UserId`. Note a retention rule when the learning-data view arrives (milestone 7).
- **R6.** `ClaudeParser.ParseAsync`: `CancelAfter` runs on wall-clock time while durations use the injected `TimeProvider`. Acceptable, but a `TimeProvider`-driven timeout would make `ATimeoutIsUnavailable` deterministic.

## Verdict
Pass with changes: fix I1 (one shared idea of a number between the masker, the validator and the resolver) and I2 (the PIN check's coverage of the learning log and the model payload, and the misleading comment) before tagging milestone 6. Khalil should rule on the typed-PIN policy and confirm M5.
