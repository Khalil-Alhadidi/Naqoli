## Summary

The nine rules hold.

- **Rule 1:** the console's side door (`WalletFaults`) names only `admin/faults` and `admin/debit`; `NoTapNoMoneyTests` still pins the literal `transactions` to `WalletClient` alone and the conversation's Confirm and settle to `ChatSession.ConfirmAsync` and `SettleAsync`. The card panel's automatic settle calls `Session.SettleAsync()` and nothing else. The external debit is a simulated outside event behind two keys; it is not a path from words to the wallet's execute.
- **Rule 2 and 3:** `biller_text` is validated (length 100, blank to null), read only by `BillResolver.NamesProvider`, and never reaches a card, the trace (the parse step traces the intent only), the audit row (`WriteRefusalAsync` takes code and detail) or the learning log (`DetailFrom(BillNotFound)` logs the validated `BillerCode`). The `FaultingParser` returns a code-built `ParsedRequest`; the inner parser's own validation is untouched.
- **Rule 5:** the oracle tokenises `biller_text` with the message's mask map before it leaves the scripted parser.
- **Rule 6:** `SettleCheckingAsync` looks the key up, traces it, and still resends the same body under `record.IdempotencyKey`; three handler tests show the outcome comes from the resend (404, done, and a lookup that gets no answer). The automatic settle and the tapped one are the same `ChatSession.SettleAsync`, serialised by `Conversation.EnterAsync` and the panel's `acting` flag.
- **Rule 9:** no key is logged or shown; `AdminKeyFilter` and `ClientKeyFilter` compare in fixed time; the console shows `set`/`not set`; refusals carry the wallet's code or the HTTP status only.
- **Wallet route:** `/admin/debit` sits inside the client-key group and the admin-key group, holds `WalletGate` exclusive, debits with one conditional `ExecuteUpdateAsync` (`BalanceIqd >= amount`), writes a `done` `externalDebit` row with fee 0 under an `admin-<guid>` key that `IsValidIdempotencyKey` refuses on execute and by-key. `AdminDebitTests` cover each of these including the key guard and reset.

No Important item was found. The Minor items are robustness and documentation: an exception class the side door does not catch (fatal to a Blazor circuit), a timer tick that can run one settle after the card panel is disposed, the daily cap's allow-list failing open on type drift with no test pinning the wallet's type set, and the failure-modes row on console reach not yet naming the external debit.

## Findings

### Minor

**M1. The side door's catch filter misses `IOException` and `ObjectDisposedException`, and the fault panel has no catch of its own; an unhandled exception in a Blazor event handler or `OnInitializedAsync` ends the circuit.**
- Where: `src/Agent.Web/Services/WalletFaults.cs` lines 105, 124, 151-153 (`IsNoAnswer` lists `HttpRequestException`, `JsonException`, `NotSupportedException`, `TaskCanceledException`); `ProblemAsync` line 136 reads the body stream with only `JsonException` caught; `src/Agent.Web/Components/Console/FaultPanel.razor` lines 109-115 and 207-223 (no try/catch around `CallAsync`).
- What: a connection dropped mid-body (`IOException` from `ReadAsStreamAsync`/`ReadFromJsonAsync`), or a disposed handler during circuit teardown, propagates out of `ApplyWalletAsync`/`DebitAsync`/`OnInitializedAsync`. Per Microsoft's Blazor error-handling docs an unhandled exception in a lifecycle method or event handler is fatal to the circuit (learn.microsoft.com/en-us/aspnet/core/blazor/fundamentals/handle-errors), so the operator's console dies mid-demo. The class comment promises "nothing is thrown to a component".
- Fix: in `IsNoAnswer` add `or IOException or ObjectDisposedException`; in the panel wrap `CallAsync` and the debit in a `try`/`catch (Exception)` that sets `error` to a fixed text (never `ex.Message`, which could echo a key-bearing URL). Add a test with a handler that throws `IOException` on the body read and assert a `Failed("unreachable")`.

**M2. The card panel's one-second tick can issue one automatic settle after the component is disposed, and the tick's task is discarded.**
- Where: `src/Agent.Web/Components/Phone/CardPanel.razor` lines 125 (`timer = new Timer(_ => _ = InvokeAsync(TickAsync), ...)`), 146 (`await SettleIfDueAsync()`), 235-239 (`timer?.Dispose()`).
- What: `System.Threading.Timer.Dispose()` does not wait for a callback in flight; a `TickAsync` already queued on the dispatcher runs `SettleIfDueAsync` after `Dispose`, and `StateHasChanged` on a disposed component. The settle is under the same key (rule 6 holds, money cannot move twice), but it is a wallet round-trip the component no longer owns, and any exception from `TickAsync` is unobserved. Same shape as review M7 R3.
- Fix: a `disposed` flag checked at the top of `TickAsync` and before `await SettleAsync()`; dispose the timer with `await timer.DisposeAsync()` in an `IAsyncDisposable` or `Timer.Dispose(WaitHandle)`; keep the discard but route exceptions to the session's error path. Microsoft's Blazor lifecycle guidance: stop timers and check disposal in callbacks that touch the component (learn.microsoft.com/en-us/aspnet/core/blazor/components/lifecycle#component-disposal-with-idisposable-and-iasyncdisposable).

**M3. The daily cap's allow-list of payment types fails open on drift, and nothing pins the wallet's type set against it.**
- Where: `src/Agent.Core/Pipeline/Checks.cs` line 56 (`PaymentTypes = { "transfer", "bill", "purchase" }`), line 139; the wallet's `TransactionType` enum in `src/Wallet.MockApi/Data/Entities/Transaction.cs` line 69.
- What: to the question "can an attacker-controlled history `type` make a payment uncounted": no. The history `type` is the wallet's enum name (`HasConversion<string>`), written by the wallet; the execute body's `type` is validated by `PaymentValidator`, so a caller cannot plant a type. The remaining risk is drift: a future wallet debit type not named here is silently left out of the cap (fail open), while a credit type must be left out. The test `ChecksWalletUnavailableTests.DailyCapCountsOnlyDonePayments` fixes today's four names only.
- Fix: a test in the `wallet-api` collection (or a pure one over `TransactionNames`) asserting that every wallet `TransactionType` is either in `Checks.PaymentTypes` or in an explicit non-payment set `{ externalDebit }`, so a new type fails the build until classified. Make `PaymentTypes` `internal` for the test.

**M4. The failure-modes row on console reach does not yet say the console can now take money from the demo wallet and arm faults.**
- Where: `docs/failure-modes.md` line 128 ("whoever reaches it can turn the kill switch off or raise the caps").
- What: with milestone 8 the same person can debit `DemoUserId`'s wallet (`fault-debit-apply`) and set the wallet's process-wide fault switch. On loopback (`AllowedHosts` localhost, `launchSettings` localhost:5089) this is acceptable for a demo and by design (ruling 4); the row should say so. Note also that in Development `AdminKeyFilter` accepts any non-empty header, so the console's `dev` key is no barrier there.
- Fix: extend row 128 and the README's console line: the fault panel is an operator control; hosting the console off loopback needs ASP.NET Core authorization on the panel and a real `Wallet:AdminKey` (learn.microsoft.com/en-us/aspnet/core/blazor/security/).

**M5. `ModelFaultSwitch.Changed` runs subscribers synchronously inside the parse call.**
- Where: `src/Agent.Web/Services/ModelFaultSwitch.cs` lines 58 and 80-81; subscriber `FaultPanel.OnModelChanged` line 119.
- What: `Take()` is called by `FaultingParser.ParseAsync` on the user's parse path. Every open console's panel is a subscriber; one that throws (for example a panel whose circuit is tearing down) turns the user's message into an exception instead of a parse. Today's subscriber only discards `InvokeAsync`, so the window is small; the coupling is the issue.
- Fix: invoke each handler in its own `try`/`catch` (or raise `Changed` on the thread pool with `Task.Run`), so the parse path never depends on a panel.

**M6. `ChatSessionTests` register their own `IParser` after `AddAgentWebServices` without re-wrapping, so those sessions run without the decorator.**
- Where: `tests/Agent.Core.Tests/Web/ChatSessionTests.cs` line 58 (`services.AddSingleton<IParser>(...)` with no `AddFaultingParser()`); contrast `FaultPanelServicesTests.cs` lines 46-50.
- What: not a production gap (`TheRegisteredParserIsTheFaultingParserOverTheScriptedParser` proves the console's registration), but the plan asked for the session tests to keep the decorator or document why not, and the summary comment of `AddFaultingParser` says a host that registers afterwards "calls it again". The session tests therefore assert slightly less than the console runs.
- Fix: add `services.AddFaultingParser();` after line 58, or a one-line comment saying the fault path is covered by `FaultPanelServicesTests`.

### Recommendations

- **R1.** `src/Agent.Web/Services/ServiceCollectionExtensions.cs` lines 96-105: an inner parser built with `ActivatorUtilities.CreateInstance` is not disposal-tracked by the container. Harmless today (`ClaudeParser` and `ScriptedParser` are not `IDisposable`, checked), but if one becomes disposable it leaks per scope. Alternative: register the original as its implementation type too and resolve it with `sp.GetRequiredService(type)`. (learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection-guidelines#disposal-of-services)
- **R2.** `ConsoleOptions.WalletAdminKey` defaults to `dev` and is only `[Required]`, so outside Development the console sends `dev` and learns of it at the first click (403 `admin_key_required`, shown as the code). Acceptable under ruling 4; a cheap fail-fast is an `IValidateOptions<ConsoleOptions>` that, when `IHostEnvironment` is not Development, requires at least `WalletOptions.MinAdminKeyLength` characters (options validation on start: learn.microsoft.com/en-us/dotnet/core/extensions/options#options-validation).
- **R3.** `FaultPanel.razor` passes no cancellation token to `GetAsync`/`SetAsync`/`DebitAsync`; a call in flight when the circuit ends runs to the client's timeout. Hold a `CancellationTokenSource`, cancel it in `Dispose` (as `LogPanel` now does after M7 R3).
- **R4.** The automatic settle (ruling 5) has no ceiling: with the wallet down, a Checking card resends every `CheckingRetrySeconds` for as long as the tab is open. Each settle is bounded by two wallet timeouts, so the cadence is self-throttling, and each resend is idempotent; still worth a line in `docs/agent-web.md` and, later, a cap or back-off setting shown in the settings panel.
- **R5.** `/admin/debit` answers `unknown_user` and `insufficient_funds` distinctly, so an admin caller can learn whether a user exists and whether the balance is at least the amount. Nothing new: the client key alone already reads `/users/{id}/balance`. Keep as is; note it in `docs/wallet-api.md`.
- **R6.** `WalletFaults.Configure` reads `IOptions<AgentOptions>` (computed once), so a live-saved `WalletTimeoutSeconds` does not reach the side door's client. Consistent with `WalletClient`; fine for a demo, but if the timeout is meant to be live everywhere, read `IOptionsMonitor<AgentOptions>.CurrentValue` in the configure delegate (it runs per typed-client creation).
- **R7.** `ProviderNames.Parenthesised` takes the first word inside the first parentheses only. Right for the seed (`(ايرثلنك)`, `(Earthlink subscription)`); a biller named `(Al Earthlink)` would give `Al`. Low risk since the seed is frozen by hash; consider every word of the parentheses as a candidate name when the biller list grows.

## Checked and found sound

- **`POST /admin/debit`** (`src/Wallet.MockApi/Services/ExternalDebitService.cs`, `Endpoints/AdminEndpoints.cs`): route in the `/admin` group with `AdminKeyFilter`, inside the root group with `ClientKeyFilter` (`Program.cs` lines 96-101). `amountIqd <= 0` is 422 `invalid_amount` before the gate; unknown user 422 `unknown_user`; the gate is exclusive for the lookup, the update and the row; one `ExecuteUpdateAsync` with `BalanceIqd >= amount` inside an explicit `ReadCommitted` transaction (sufficient under the exclusive gate; the balance-after read sees its own update); zero rows rolls back with nothing written; no arithmetic overflow (`balance >= amount >= 1`). The key is `admin-` plus a GUID; `IsValidIdempotencyKey` refuses both `seed-` and `admin-` prefixes without case on execute and on by-key (`TransactionEndpoints.cs` lines 58 and 79). Nothing logged. `DebitRequest(int, long)` binds strictly; a malformed body is a 400 from minimal APIs. Tests: `AdminDebitTests` (lower-and-row, below-zero, admin key, zero/negative, unknown user, key neither replayed nor looked up, reset).
- **The side door** (`src/Agent.Web/Services/WalletFaults.cs`, `ConsoleOptions.cs`): two route constants only, `admin/faults` and `admin/debit`; the admin key goes into a default header once and is never read back, logged or shown; results carry the wallet's `code` or the status digits; `SettingsPanel` renders `set`/`not set`. Typed client registered once; the panel resolves it in a fresh scope per call.
- **The decorator** (`FaultingParser.cs`, `ModelFaultSwitch.cs`, `AddFaultingParser`): `Take()` reads and clears a once fault under one `Lock`, so two concurrent parses cannot both take it; the switch is a `TryAddSingleton`; the decorator keeps the original lifetime (singleton scripted, scoped Claude) and resolves the inner from the same provider; keyed registrations are skipped; the last non-keyed `IParser` is wrapped, and `FaultPanelServicesTests` proves the console's resolved `IParser` is `FaultingParser` over `ScriptedParser` and that an armed `unreachable` yields `model_unavailable` once with no card. Model text cannot bypass validation: the decorator fabricates only `Unclear`/`injected`, which `Conversation` already routes to `model_invalid_reply`.
- **The fault panel** (`FaultPanel.razor`): delay and amount parsed with `NumberStyles.None` and the invariant culture (no sign, no whitespace; overflow fails the parse); the wallet bounds the delay (`MaxFaultDelayMs`, 422 `invalid_fault_delay`); every rendered value (`@error`, `@debitResult`, `@WalletStateText`, `@row.Type` in the wallet panel) is Razor-encoded; no raw markup. The debit targets `DemoUserId` only and is a wallet-side event with its own history row; it cannot reach execute. The state shown is always read back from the wallet or the switch.
- **The Checking state** (`ConfirmHandler.SettleCheckingAsync`, `CardPanel.razor`): the lookup comes after the kill-switch check and before `settle_sent`, is traced in the Write zone with status, `unknown_key` or `unavailable <reason>` (no PIN, no purchase code, no balance), and never selects an outcome branch; the resend uses `record.IdempotencyKey` and `RequestFrom(record, pin: null)`. Tests: `TheSettleLooksTheKeyUpAndTracesUnknownKeyWhenNothingWasWritten`, `...TracesDoneWhenTheWalletPaid`, `ALookupThatGetsNoAnswerDoesNotStopTheSettle`, `ConcurrentSettlesSettleOnce`. On screen: `SettleIfDueAsync` skips when `Session.Busy` or `acting`; both the tick and the tap set `acting` synchronously on the circuit dispatcher before any await; `Conversation.SettleAsync` is behind `EnterAsync` and re-reads `CardState == Checking`; a late click on a disabled button therefore becomes a no-op. `CheckingRetrySeconds` is `[Range(1, 600)]`, default 5, in both appsettings, in `RuntimeSettings.EditableNames` and read from `IOptionsMonitor.CurrentValue` per tick. Journeys 7 and 8 assert zero `not_done` outcomes at the Checking point and at the end, one history row, one `done` audit row.
- **`biller_text`** (`ParsedRequestDto.cs`, `ParsedRequestValidator.cs`, `BillResolver.cs`, `ProviderNames.cs`, `ArabicText.cs`): bounded at 100 UTF-16 units before anything else reads it; `ArabicText.Words` is NFC plus a rune walk that drops format characters and harakat and collapses whitespace, with no regex and no allocation proportional to anything but the input, so hostile input is safe; comparison is `ArabicText.Key` equality against names taken from the wallet's own biller strings, so the text is never used as a pattern, a path, a query or markup. The orchestrator's bill subject uses `bill.Label ?? bill.BillerName` from the wallet.
- **Part of a bill** (`Orchestrator.cs` lines 164-170, 456-508; `Conversation.AnswerForOption` lines 856-869): the request becomes `Bill` with the reason kept; it passes the kill switch and consent gates; every `BillCardAsync` entry (tapped bill, `Card`, `AskBillOrStore when partial`) returns `RefuseAsync(BillsPaidInFull, PartOfBill, bill.AmountDueIqd)` before any check, quote or `CheckAndIssueAsync`; `Options` asks `which_bill` and the tap keeps the partial request so the tapped bill is refused the same way; `StoreInternet when partial` is `bill_not_found`; the audit row holds code and detail only; the figure in the reply is the wallet's `AmountDueIqd`.
- **The runner** (`WalletAdmin.ExternalDebitAsync`, `CaseDriver` lines 170-179, `CaseGrader` lines 310-311): the debit happens only while the card is live, once per case, its transaction id alone is excluded from the diff, a failure is a step error; `amount_due` is graded against the matched refusal's figure and fails when the reply has none (`ARefusalAmountDueIsGraded`).
- **Journeys**: `JourneyHost.ResetAsync` clears each console's `ModelFaultSwitch`; the wallet reset clears its switch; every fault journey ends with `AssertFaultsClearedAsync`.
- **Secrets and logging**: no new logger calls in the diffed files; `appsettings.json` carries only the non-secret `dev` default; no PIN, balance or purchase code enters a trace, an audit row or a learning row on any new path.
