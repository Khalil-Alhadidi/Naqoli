# Milestone 5: Test Set and Runner (the Gate) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task (one implementer agent for the whole milestone, per Khalil's rule of 14 Oct 2026; the controller reviews each task's diff itself). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `Agent.Eval` runs a request set through the same conversation logic as the phone, simulates every step form of `data/README.md` (typed messages, option taps, Confirm with a correct or wrong PIN, double taps, cancel, waiting for the timer), grades every card field, every question, every reply code and the final wallet state against the answer key, performs the three per-case checks of D12 (no phone, account number or balance in the outbound parser text; time and cost; the learning-log entry where the key expects one), and writes a report with counts, percentages and ranges per category. The grader has its own tests. The runner completes on the development set with the scripted parser.

**Architecture:** The conversation logic of milestone 4 (`ChatSession` in `Agent.Web`) moves into `Agent.Core` as `Conversation`, a headless state machine over `IParser`, `Orchestrator`, `ConfirmHandler` and `PendingStore` that exposes codes and figures, never text; `ChatSession` becomes a thin adapter that localises and raises UI events. `Agent.Eval` references `Agent.Core` only and talks to a running wallet over HTTP (reset and faults through the admin routes). It loads a case file, plays each case through a fresh `Conversation` with a controllable clock, a recording parser wrapper and the wallet's fault switch, snapshots the wallet before and after, grades, and writes JSON and Markdown reports that carry case ids and codes but never case text. The held-out file can only be read with an explicit flag, and the report records the file's SHA-256 next to the committed hash.

**Tech Stack:** .NET 10 console (`Agent.Eval`), `System.Text.Json` (snake_case, strict), `Microsoft.Extensions.Hosting` for DI in the console, `TimeProvider`, xunit.v3; no new packages expected.

**Spec:** `docs/build-plan.md` milestone 5 ("Done when" lines); `docs/architecture.md` D12, D13, D14, D22, section 5; `data/README.md` (the case format, step forms, reason codes, answer-key semantics, "A case passes when..."); `data/seed/settings.json` (learning-log reasons); `docs/agent-core.md` and `docs/agent-web.md` (what exists); the rulings in memory. Project rules: `CLAUDE.md`. Repository root: the clone folder.

## Global Constraints

- Six projects only. `Agent.Eval` references `Agent.Core` only (never `Wallet.MockApi` or `Agent.Web`). The runner drives `Conversation`, never the screen.
- **Rule 7.** `data/requests.heldout.jsonl` is read only by `Agent.Eval` with the explicit argument `heldout --milestone-11-run` (both required); without the flag the runner refuses and prints the rule. No test, script, fixture or report reads, prints, copies or summarises it. The dev set (`data/requests.dev.jsonl`) is the only set used in tests and in this milestone's run. Reports carry case ids, categories, codes, figures and verdicts, never a case's message text. The implementer may read the dev set to build the runner; the controller does not need it.
- Rule 1 stays proven: `Conversation.ConfirmAsync` and `Conversation.SettleAsync` are the only callers of the handler in `Agent.Core`; `ChatSession` and the runner's `CaseDriver` are the only callers of those two in `Agent.Web` and `Agent.Eval`; the IL test scans all three assemblies and asserts the sets.
- Rule 3 and 4 in the grader: the grader compares codes and figures; it never generates text. Khalil's answer keys, targets and `docs/matching-rules.md` are never edited to make a case pass (rule "Things only Khalil writes"); a mismatch is reported as a failing case with its diff.
- Rule 8 and 9: synthetic data; the runner's wallet admin key and client key come from configuration or environment, never the repository (Development open mode: any non-empty header).
- No Arabic in C#. The runner never logs or prints case text; the PIN values come from `data/seed/users.json` at run time (read by the runner through a tiny record; the file is Khalil's synthetic seed) and never appear in reports or logs.
- The learning log table does not exist until milestone 6: `LearningLogRule.EntryFor(AgentReply, ...)` in `Agent.Core` is the pure function that decides what milestone 6 will persist (reason in `settings.json` `learning_log.logged`, with its detail); the runner grades that derived entry now, and milestone 6 persists exactly it.
- Cost: `IParser` implementations may implement `IParserUsage` (`ParseUsage? LastUsage` with `InputTokens`, `OutputTokens`, `CostUsd`, `Duration`); the scripted parser reports zero; the runner records it.
- Limits are configuration (`Eval` section: `SetDirectory` default `data`, `ReportDirectory` default `docs/reports`, `WalletAdminKey`, `CaseTimeoutSeconds` 60, `SettleAttempts` 3, `SettleDelayMs` 200) shown in the report header.
- Microsoft guidance: `Host.CreateApplicationBuilder` for the console, `System.Text.Json` source-compatible options, `Stopwatch`/`TimeProvider`, xunit.v3. Every new failure mode gets a `docs/failure-modes.md` row; every package a `docs/disclosure.md` line. Build 0 warnings; small commits with the trailer lines; stage files explicitly.

## Review Focus

- A case whose card has one wrong field (for example the fee) is graded as failing with that field named; a case whose expected card never appears is failing; a case with an unexpected card is failing. Grader tests in Task 3.
- A Confirm step that the runner does not reach (the card never appeared) counts as no execution: the wallet shows no new transaction and the case fails on the missing card, never on a phantom execution. Test in Task 3.
- The outbound-text check fails a case when the text handed to the parser contains any seed phone number, any wallet account number or the user's balance figure, in ASCII or Arabic-Indic digits. Tests in Task 2.
- The held-out guard: `Agent.Eval heldout` without the flag exits non-zero and reads nothing; with the flag it computes and prints the file hash next to the committed one. Test in Task 3 (with a temporary set directory holding a dummy `requests.heldout.jsonl`, never the real one).
- Wallet reset and agent reset per case: the balance, the pending records and the audit log start fresh, and the agent clock is reset to real time so the Iraq-date daily cap is right. Test in Task 2.

**Driver semantics (`CaseDriver.PlayAsync(EvalCase, ct)` → `CaseObservation`):** reset the wallet (admin) and the agent (`PendingStore.ExpireAllOpenAsync("wallet_reset")` + clear audit), reset the clock to real now, snapshot the wallet; create a `Conversation` for the case's user (map `U1` → wallet user by code through `WalletClient.GetUserAsync` over ids 1..5 or a `users.json` lookup); for each step: `say` → `SendAsync`; `tap option` → `TapOptionAsync(value)` where `value` is used as given (contact/bill/product/operator code, `store:internet`, or an amount in dinars as digits); `tap confirm` → `ConfirmAsync(pin)` with `pin` = the user's seed PIN for `correct`, `0000` for `wrong`, null otherwise; `twice` → two concurrent `ConfirmAsync`; `tap cancel` → `CancelAsync`; `tap try_again`/`save_alias` → observation `UnsupportedStep` (D19 and 9a not built); `wait expire` → advance the clock past the card's `ExpiresAt` plus one second, run `PendingStore.ExpireDueAsync` through a scope, then `RefreshAsync`; `wait expire_if_card` → the same when a card is live, else nothing; `fault.on == "request"` → arm the parser fault before the first `say`; `fault.on == "confirm"` → set the wallet fault (`wallet_error` → `error`, `wallet_timeout_before_execute` → `timeoutBeforeExecute`, `wallet_timeout_after_execute` → `timeoutAfterExecute`, `once: true`, `delayMs` = the runner's `FaultDelayMs` 3000) before the first `tap confirm`; `fault.code == "external_debit"` with `on == "card_waiting"` → after the card appears and before the next step, run the external debit; after a `Checking` outcome the driver settles up to `SettleAttempts` times with `SettleDelayMs` between (recording the `status_sequence`); after each step record the step's observations (card state, outcome code, reply codes since the step began, money moved so far, executions = new `done` transactions, attempts left from a `PinWrong`, whether a new card replaced the previous, whether the PIN string occurs in any message code/figure, trace detail or audit row); at the end snapshot the wallet again, diff, collect `CardsIssued`, `QuestionsAsked`, the reply messages (codes with figures), the consent screen flag, the derived learning entry (`LearningLogRule` applied to the last orchestrator reply of the case: expose it from `Conversation` as `LastReply`), the parser texts and usage, and the elapsed time. Every exception inside a step is captured as `StepError` on the observation (the case fails; the run continues).
