Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every deliverable of milestone 9a in `docs/build-plan.md`: the offer to save an alias after a completed payment that needed a question (rule 18), saved only on the user's tap; the directory to manage aliases, in the console and on the phone; options to tap for a near match on a saved alias (rule 6 over aliases); rule 18 goes from `no` to `yes` in `docs/rules-coverage.md`. Done when the alias cases of the development set (AMB-19, AMB-19-v1) pass on the oracle with `alias_offer` and `final.alias_saved` graded, an alias always points to exactly one account, and alias text never reaches the model (`OutboundPayloadTests` extended to a conversation with a saved alias). One screen journey per behaviour, on the oracle.

**Architecture:** The wallet owns aliases already (`Aliases` table, `GET /users/{id}/contacts`, the seed's nine, the reset); it gains the two write routes `POST /users/{id}/aliases` and `DELETE /users/{id}/aliases/{aliasId}`. `Agent.Core` gains an `Aliases` folder: the pure offer rule (`AliasRule`), the directory service that validates and writes through the wallet (`AliasDirectory`), and the offer on the conversation (`Conversation.AliasOffer`, `SaveAliasAsync`, the directory actions). The resolver reports which matching step produced a question (`Resolution.Options.Step`), which is what rule 18 needs. `Agent.Web` shows the offer under the Done outcome with one Save button, a directory screen inside the phone (Arabic, `TODO-AR` keys) and an Aliases panel in the console menu (English). `Agent.Eval` plays `tap save_alias`, observes the offer and grades `alias_offer` and `final.alias_saved`. A biller alias ("my اشتراك" pointing to one biller account) is the later item of the build plan and is not built; `AliasDirectory` takes only an account.

**Tech Stack:** .NET 10, Blazor Server with MudBlazor 9, EF Core (no migration: the `Aliases` table and its unique index on `(OwnerUserId, Text)` exist since milestone 2), xunit.v3, Playwright. No new package. If one is needed, it gets a `docs/disclosure.md` line in the same commit.

**Spec:** `docs/build-plan.md` milestone 9a ("Delivers", "Done when", the later biller-alias item); `docs/architecture.md` D15 (distinct aliases, offered after a completed payment, saved with approval or managed in the directory, exact goes to the card, near shows options, never a bare name shared by several, alias text never reaches the model), D16 (the card shows the alias with the registered name under it), D21 (to reach someone new the user types a number or saves an alias for them); `docs/matching-rules.md` rules 2, 6, 7, 18 and "Recipients"; `docs/wallet-api.md` (`AliasItem`, `ContactsResponse`, ProblemDetails with `code`); `CLAUDE.md` rules 1 to 9; `docs/agent-core.md`, `docs/agent-web.md`, `docs/agent-eval.md` as the record of what is built; `data/README.md` (`tap save_alias`, `alias_offer`, `final.alias_saved`).

## Rulings taken by the controller (for Khalil to confirm)

> **Khalil's answer, 18 Oct 2026 (recorded at the close-out, `docs/plans/milestone-9a-close.md`):** rulings 1 to 9 below confirmed, with the two taken during the tasks (the alias routes take the wallet gate shared, as the consent route does; the plan's test "a saved alias never reaches the parser" reinterpreted, the guarantee living in `OutboundPayloadTests.ASavedAliasNeverReachesTheModel`). Of the security review's four recommendations: a closed target account is refused at save (`account_closed`); a bare first name shared by several saved names is refused at save (`alias_shared`, the new string `Refusal_alias_shared`); the offer shows the registered name as `{1}`; a user aliasing their own second number stays documented inside the D10 known gap. His wording for the sixteen `TODO-AR` keys and the new one landed the same day.

1. **Where an alias lives.** In the wallet, as now: the agent writes it through two new wallet routes and reads it back with the contacts. The runner's `final.alias_saved` compares the wallet's aliases before and after the case. The agent database holds no alias.
2. **"Needed a question" and "not a bare name shared by several contacts" (rule 18)** read from the resolver's steps: the recipient reached the card through a tapped option, and the question came from the near step (rule 6), the shared-word step (rule 15) or the title-only step (rule 5, always one candidate). An exact hit on several accounts (rule 3) or a partial hit on several (rule 4) is a bare name shared by several: no offer. So 'حسين القصاب' and 'علي الحلاق' are offered; 'حسين' and 'علي' are not; a near spelling ('ابو المولد') is offered as typed, since rule 18 names no exception for it.
3. **The offered text** is the recipient as the user typed it (AMB-19-v1: "the offered alias follows the user's spelling"), and it is shown only when it occurs verbatim in a message the user typed (a typed answer the code read, or the model's `recipient_text` found inside the typed message, ordinal). A `recipient_text` the model did not copy verbatim gives no offer; the payment is untouched. This keeps rule 4: the phone never shows model text.
4. **Distinct (D15, "an alias always points to exactly one account")**: the wallet's unique index is on the raw text per owner; the agent refuses a new alias whose key (`ArabicText.Key`) equals the key of any saved name or alias the user already has, on any account (`alias_exists`), so an alias can never create an exact hit on two accounts, and never shadows a saved name. Also refused `alias_invalid`: blank, longer than `MaxAliasLength`, a key of zero length, or text that looks like a phone number (`PhoneNumbers.LooksLikeNumber`).
5. **The directory** lists, adds and deletes; there is no rename (delete and add). On the phone it is a screen behind a button in the phone's header, with its own `TODO-AR` strings; in the console it is a side-menu panel, "Aliases", in English. Both act on the demo user's wallet through the same `AliasDirectory` and the same `ChatSession`. An alias may be added for one of the user's contacts (picked from a list) or for a typed phone number (D21), resolved by the wallet's by-phone route.
6. **What the audit log keeps**: `alias_saved` and `alias_deleted` rows with the account id as the detail, never the alias text (the wallet holds the text). The trace shows `alias_offered`, `alias_saved`, `alias_deleted` and the refusal codes, never the text. The learning log is untouched (an alias action is not a request).
7. **The offer lives until the next user action**: it is shown under the Done outcome and cleared by the next typed message, tap, reissue or save. AMB-19's second request therefore asks again, and nothing is saved (the key's `alias_saved: null`).
8. **`MaxAliasLength`** is a new agent setting (default 100, the wallet column's length), shown in the settings component and editable; the wallet refuses a longer text as `alias_text_invalid` anyway.
9. **Grading `alias_offer`**: a step's `"alias_offer": "<text>"` passes when the step showed an offer with exactly that text (ordinal); an explicit `"alias_offer": null` passes when the step showed none; an absent key grades nothing. `final.alias_saved` is always graded: `null` passes when the case left the wallet's alias list unchanged; a text passes when exactly one alias was added and its text is that text.
