# Milestone 3: Write Path, No Model Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything between the model and the wallet exists in `Agent.Core` and is proven by tests that feed it a hand-built structured request: resolver (contacts, aliases, typed numbers, bills, products) following `docs/matching-rules.md`, quote, the checks in Khalil's order, the pending store and state machine of architecture section 5, the executor behind the Confirm handler, and the audit log; plus the wallet hardening the milestone 2 and 2b reviews required before any client talks to it.

**Architecture:** `Agent.Core` is a class library with its own EF Core context (`AgentDbContext`, database `ZainCashAgent`, tables `PendingTransactions` and `AuditEntries`), a typed `HttpClient` for the wallet (`WalletClient`, contract records mirrored from `docs/wallet-api.md`, no shared assembly), pure text and resolver code with no I/O, an `Orchestrator` that turns one `ParsedRequest` into a question, a refusal, a balance reply or a pending record with a card, and a `ConfirmHandler` that is the only code able to reach the wallet's execute call. Replies are reason codes in this milestone; the phone strings come in milestone 4. The model, masking and the parse call come in milestone 6; the structured request type they will produce is defined here and built by tests.

**Tech Stack:** .NET 10, EF Core 10 SqlServer 10.0.13 (+ Design for migrations), `Microsoft.Extensions.Http` 10.0.x (typed client via `IHttpClientFactory`), `Microsoft.Extensions.Options.DataAnnotations` 10.0.x, `TimeProvider`, xunit.v3 4.0.2, `WebApplicationFactory` for the in-process wallet. No resilience package (retries carry the same key by our own code).

## Global Constraints

- Six projects only. `Agent.Core` never references `Wallet.MockApi`; it talks HTTP. The test project references both and hosts the wallet in process.
- Rule 1: only `ConfirmHandler.ConfirmAsync` and `ConfirmHandler.SettleCheckingAsync` call `WalletClient.ExecuteAsync`; an architecture test scans the IL of every method in `Agent.Core` and fails if any other method references it.
- Rule 2 and 3 groundwork: `ParsedRequest` is a request to check; every figure on the card comes from the wallet (`/quotes`) or the catalogue, never from the request's free text.
- Rule 4: no reply text exists in `Agent.Core`; replies are reason codes (`ReasonCodes`) and question kinds (`QuestionKinds`) from `data/README.md`.
- Rule 5 groundwork: wallet response types live in `Agent.Core.Wallet` and nothing outside `Agent.Core.Wallet`, `Agent.Core.Resolver`, `Agent.Core.Pipeline`, `Agent.Core.Confirm` may reference them; `ParsedRequest` carries only the user's own words and numbers.
- Rule 6: one key per pending record, `Guid.NewGuid().ToString("N")`, stored, reused on every retry; a pending record leaves `Pending` only once (conditional update); a 500 (with or without `code`), 504, client timeout or dropped connection is `Checking`, never `NotDone`; `Checking` settles only by resending the same body with the same key.
- Rule 7: nothing in this milestone reads `data/requests.heldout.jsonl` or `data/requests.dev.jsonl`. Resolver test inputs are Khalil's examples transcribed from `docs/matching-rules.md` into a JSON test file; the seed's Arabic comes from `SeedSet` through `SeedFacts`.
- Rule 8 and 9: synthetic data only; the wallet client key and the agent connection string live in user secrets or environment variables; tests use `ConnectionStrings__AgentTest` (default `Server=localhost;Database=ZainCashAgent_Test;Trusted_Connection=True;TrustServerCertificate=True`, name must end `_Test`).
- No Arabic in C#. Arabic letters needed by the normaliser are `\u` escapes with the letter's Unicode name in the comment; Khalil's kinship and title words (rule 1) live in `src/Agent.Core/Text/arabic-words.json` (embedded resource), transcribed verbatim from `docs/matching-rules.md`.
- Khalil's wording is never changed: `docs/matching-rules.md` is read, not edited; a rule that cannot be implemented as written is reported, not reinterpreted.
- Limits are configuration: `AgentOptions` (section `Agent`) with the values of `data/seed/settings.json` as defaults, pinned by a test, shown in the settings component in milestone 7.
- Check order (matching rules, "Order of checks"): 1 format, 2 recipient (or bill, or product), 3 per-transaction cap, 4 daily cap, 5 balance on the total. The first failing check is the reason returned. The daily cap counts amounts without fees, transfers, bills and purchases together, over the Iraq date of today (UTC+3), because seeded rows at `days_ago` 0 can be later than "now".
- Follow Microsoft's documented guidance: typed `HttpClient` through `IHttpClientFactory` with `AddHttpClient<T>` and `ConfigurePrimaryHttpMessageHandler` in tests, `HttpClient.Timeout`, `ProblemDetails` parsing, EF Core conditional `ExecuteUpdateAsync` for state transitions, migrations with a design-time factory, options validation on start, `TimeProvider`, `ILogger` with `[LoggerMessage]` and no PIN, balance or code in any log line (`System.Net.Http.HttpClient` logging at Warning).
- Every package added gets a `docs/disclosure.md` line in the same commit. Every new failure mode gets a `docs/failure-modes.md` row.
- Build with 0 warnings. Commits: English, imperative, small; end with the two attribution trailer lines given in the dispatch. Stage files explicitly.
- Run one class: `dotnet test tests/Agent.Core.Tests -- --filter-class "Agent.Core.Tests.<Namespace>.<Class>"`.

## Review Focus

- Two Confirm calls for one pending id, concurrent: exactly one execute reaches the wallet, one balance change, the second caller gets the stored outcome. Test in Task 6.
- Confirm after the card timer: the record goes `Pending → Expired` and the wallet is never called; a cancelled record likewise. Test in Task 6.
- The wallet returns 500 or hangs past the client timeout after committing: the record is `Checking`, the key is kept, `SettleCheckingAsync` resends the same key and finds `Done` with the same reference, money moved once. Test in Task 6.
- The balance falls after the card is built (another payment lands): Confirm rechecks, the record is `NotDone` with `insufficient_balance`, nothing moves; and the wallet's own conditional debit is the last line of defence when the balance falls between the recheck and the execute. Test in Task 6.
- A typed name that is one letter away from an alias (`اخوية حمدي`) gives a question with that one option, never a card. Test in Task 3.

**Interfaces:**
- `ClientKeyFilter : IEndpointFilter`, header `X-Wallet-Client-Key`, same rules as `AdminKeyFilter`: with `Wallet:ClientKey` configured (min 16 chars, `[MinLength]`), the header must equal it (`FixedTimeEquals`); with none configured, open in Development only and only when the header is present with a non-empty value; closed elsewhere. 403 code `client_key_required`. - `Transaction.RequestFingerprint` (string, 64, not null): SHA-256 lower hex of the canonical string `$"{UserId}|{Type}|{AmountIqd?.ToString() ?? ""}|{ToPhone ?? ""}|{ToAccountId?.ToString() ?? ""}|{BillAccountId?.ToString() ?? ""}|{ProductId?.ToString() ?? ""}"` computed from the request body as received (before validation) by `static string RequestFingerprint.Of(PaymentRequest)` in `Services/RequestFingerprint.cs`. On insert the row stores it. On replay (`LoadAsync` found a row, in `ExecuteCoreAsync` and `RefuseUnlessKnownAsync`) a different fingerprint is refused with 422 `idempotency_key_reused` and no stored body. Seeded rows store the fingerprint of `(userId, type, amount, toPhone of the recipient, null, bill id, product id)`.
- `Transaction.BalanceAfterIqd` (long?, null for seeded rows): set in `RunAsync` to the payer's balance after the debit and credit, inside the transaction. `ToResponseAsync` uses the stored value when present, else the current balance (seeded rows only; documented).
- `GET /transactions/by-key/{key}?userId=` : `userId` required (`[FromQuery] int? userId`; missing → 400 `missing_user_id`); a row whose `UserId` differs → 404 `unknown_key`.
- Malformed PIN: in `CheckPinAsync`, before reserving an attempt, `pin` must match `^[0-9]{4,6}\z` (`[GeneratedRegex]`); otherwise 422 `pin_malformed`, no attempt counted, no user row change. Title "PIN must be 4 to 6 digits".
- Closed payer: `PaymentValidator.ValidateAsync` selects `Status` with the payer account; `Closed` → 422 `account_closed` (same code as a closed recipient), checked right after `unknown_user`.
- `seed-` prefix: `TransactionService.IsValidIdempotencyKey` returns false for keys starting with `seed-` (ordinal); execute → 400 `invalid_idempotency_key`; by-key → 404. Seeded rows keep their keys.
- `POST /admin/debit` is documented in `docs/wallet-api.md` under a "Planned (milestone 8)" heading: body `{ "userId": 1, "amountIqd": 5000 }`, admin key, runs under the gate exclusive, debits the default account (conditional, `insufficient_funds` if it would go below zero), writes a `Transaction` of a new type `externalDebit` with fee 0 so history shows it; not built in this milestone.
