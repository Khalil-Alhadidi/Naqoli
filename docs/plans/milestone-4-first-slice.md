> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task (one implementer agent for the whole milestone, per Khalil's rule of 14 Oct 2026; the controller reviews each task's diff itself). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The layout B console in `Agent.Web` with the phone frame on the right: the Hammoudi request typed in the phone shows the card built by code, Confirm with a timer moves the money in the mock wallet, the wallet data component shows the new balance and history row, the live trace shows each step with its zone, the phone frame is right to left and the console left to right, and three Playwright journeys pass with the scripted parser.

**Architecture:** `Agent.Core` gains the parser seam (`IParser`, with `ScriptedParser` as the only implementation until milestone 6), a trace sink (`ITraceSink`) the orchestrator and the Confirm handler write to, a card view model, the write-path follow-ups the milestone 3 reviews parked, and Khalil's four code decisions of 14 Oct 2026. `Agent.Web` (Blazor Server, MudBlazor 9) gets layout B: side menu, selected console component in the middle, live trace always visible, phone frame (RTL, Arabic-Indic digits) on the right; a per-circuit `ChatSession` that opens a DI scope per user action; a hosted `PendingSweeper` for expiry and stale Executing; one resource file of phone strings with `TODO-AR` placeholders for Khalil. `Agent.Web.Journeys` hosts the wallet and the web app in process (`WebApplicationFactory.UseKestrel()`) and drives them with Playwright.

**Tech Stack:** .NET 10, Blazor Server with global interactive server rendering, MudBlazor 9.11.0 (`MudRTLProvider`, `MudLayout`, `MudDrawer`, `MudCard`, `MudTextField`, `MudTimeline`/`MudList` for the trace), `Microsoft.Extensions.Localization` with a `.resx` resource (`IStringLocalizer`), `IHostedService`/`BackgroundService`, `IServiceScopeFactory`, Playwright for .NET 1.63.0, `Microsoft.AspNetCore.Mvc.Testing` 10.0.13 with `UseKestrel`.

**Spec:** `docs/architecture.md` v0.11 (sections 2, 3, 4, 5; D2, D3, D6, D8, D16, D17 layout B, D19 groundwork, D20, D22), `docs/build-plan.md` milestone 4, `docs/agent-core.md` (the write path as built; "Decisions by Khalil (14 Oct 2026)" table), `docs/reviews/milestone-3-security-review.md` (forward-looking for milestone 4), the memory of Khalil's rulings. Project rules: `CLAUDE.md`. Repository root: the clone folder.

## Global Constraints

- Six projects only. `Agent.Web` references `Agent.Core` only; it never references `Wallet.MockApi`. Journeys reference `Agent.Web` and `Wallet.MockApi` (hosting both in process) and use the scripted parser, never a live model.
- Rule 1: the only callers of `ConfirmHandler.ConfirmAsync` and `SettleCheckingAsync` are the card component's Confirm handler and the session's settle path; the IL test extends to `Agent.Web` and asserts exactly that set. A typed "yes" never calls Confirm (D6: it points to the button).
- Rule 3 and 4: every card field and every reply on screen comes from `CardView`/`AgentReply`/`ConfirmOutcome` figures and the resource file; no generated text. New resource keys get English placeholders prefixed `TODO-AR:` and are listed in the task report for Khalil. The scripted parser's sentences are also Khalil's to write: the one placeholder sentence is English and marked `TODO-AR`.
- Rule 5 groundwork: the trace and the screen never show the PIN, the idempotency key, a full purchase code or an unmasked phone of another user; names from the wallet render through Razor encoding inside `<bdi>`, never `MarkupString`.
- Rule 7: nothing reads `data/requests.*.jsonl`. Rule 9: no secrets; the journeys use test keys. No Arabic in C# or Razor (Arabic appears only through the resource file values Khalil writes, seed data, and `ArabicDigits`).
- D20: inside the phone frame everything is right to left with Arabic-Indic digits (`ArabicDigits.ToArabicIndic`); typed input accepts both digit forms (`ParsedRequest` numbers are already parsed; the scripted parser normalises digits before matching). Everything else on the page is English, left to right.
- D17 layout B: side menu (Phone chat is always on the right; menu selects the middle component: Wallet data, Settings (placeholder), Log (placeholder), Learning data (placeholder)); live trace always visible between the middle component and the phone.
- Limits are configuration shown in settings: new `AgentOptions` entries `DemoUserId` (1), `SweepIntervalSeconds` (5), `StaleExecutingAfterSeconds` (40 = 3 × wallet timeout + margin, per the milestone 3 re-review), `MinSubstringWordLength` (3, moved from the resolver constant). The settings component itself is milestone 7; this milestone shows them read-only in a small "Settings (read only)" placeholder so the rule holds.
- Blazor Server rules from the milestone 3 security review: every UI action opens its own `IServiceScopeFactory.CreateAsyncScope()` and resolves `Orchestrator`/`ConfirmHandler`/`PendingStore` from it; no `AgentDbContext` is injected into a component; the PIN field is `type="password"`, `inputmode="numeric"`, `autocomplete="off"`, cleared after the call; option taps are validated server-side against the options offered in that session; `AgentReply.CardIssued` is projected to a `CardView` before it reaches a component (no `IdempotencyKey`, `QuotedBalanceIqd` or `RowVersion` in markup).
- Microsoft guidance: Blazor Server with EF Core (scope per operation), `BackgroundService` with `IServiceScopeFactory`, `IStringLocalizer` with `.resx`, MudBlazor RTL provider, Playwright for .NET with `IPage` locators and `Expect` assertions, `WebApplicationFactory.UseKestrel()`.
- Every package added gets a `docs/disclosure.md` line in the same commit; every new failure mode a `docs/failure-modes.md` row. Build 0 warnings; commits small, English, with the two trailer lines from the dispatch; stage files explicitly.

## Review Focus

- A double tap on Confirm: the button disables on the first click and the second call, if it reaches the server, gets `AlreadyHandled`; one wallet row, one balance change. Journey in Task 3.
- The timer ends while the card is on screen: the button is disabled, the card shows expired, and a late server call returns `Expired`; nothing moves. Journey in Task 3 with a short `CardTimerSeconds` in the journeys host.
- The circuit reconnects or two UI events overlap (timer expiry refresh and a tap): no "second operation on this context" exception, because each action has its own scope. Test in Task 2 (two concurrent actions on one session).
- The phone frame is RTL with Arabic-Indic digits while the console is LTR with ASCII digits; the card's figures equal the quote's. Journey assertions in Task 3.
- The trace never contains a PIN, a key or a full purchase code after a PIN payment and a purchase. Test in Task 2.
